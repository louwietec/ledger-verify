# Cloud Messages: Activation, Heartbeat, Anchor

**LEDGER Specification · spec_version 1.10 · Language: English (German version: `heartbeat.de.md`, identical structure)**

**Draft of edition 1.10, as of 2026-10-26: not released.** New in this edition are the vendor log with fillers, the timestamp profile, the anchor history as auditor input, the key roles with `statement_signatures`, the evidence level, the report members and the access chain with the entry type `DATA_ACCESS`. Both reference verifiers implement this edition as a draft; until it is released, verification follows the edition named by `--version` of the verifier in use.

The canonical field source is `spec/registry.json`, section `cloud_messages`. If this document and the registry ever diverge, the registry prevails.

## 1. Purpose and scope

This document exhaustively specifies all message traffic from the LEDGER appliance to the vendor metadata server. There are **exactly three message types**:

| Message type | Direction | Frequency |
|---|---|---|
| `activation` | appliance → vendor | at commissioning; again only in the cases of §4 |
| `heartbeat` | appliance → vendor | hourly |
| `anchor` | appliance → vendor | every 5 minutes |

No further message type and no further channel to the vendor exists. What the vendor answers is governed by §9. From edition 1.10 the anchor history (§9.7) and the vendor log (§9.9) are fetched from the vendor by the auditor, never by the appliance; for them there is no further message type and no further channel from the appliance to the vendor. Every sent message is chained verbatim (exact JCS bytes) by the appliance as an `ADMIN` entry in its own ledger and can be inspected in the portal under "What we send". An auditor can compare actual network traffic captures against this published schema.

**Update bundles (from edition 1.9).** Outside these three messages the updater fetches update bundles over HTTPS from the source configured at installation: the metadata server or the vendor's download area, a second address. It only asks for a bundle with `GET` and sends nothing about the installation beyond what any HTTPS request discloses (address, time, the bundle's path; the path names the version and, from the addition of 2026-10-07, the installation's architecture, `amd64` or `arm64`, §9.3); in particular never the licence key, the commitment, `license_proof` or a device identifier. The source is not a trust anchor: every bundle MUST be signature-checked against the update key pinned at installation before any use, wherever it comes from, and is discarded without a valid signature; the checksum from the update notice (§9.3) protects the transport only. If a source requires an authorisation, its form is defined in this specification before it is built; sending the licence key for it is excluded. The updater's requests are not messages in the sense of this document and are not chained; an installed update evidences itself in the chain through its handover (`SEAL` with `reason = update`, `RESUME`).

**Time witness (format specification 7.3).** Also outside the three messages, the appliance MAY request timestamps per RFC 3161 from a time-stamping authority that the customer has set up. The request goes directly to the authority, never through the vendor, and carries the imprint over the signature subject of a checkpoint (format specification 7.3). It is not a message in the sense of this document; the appliance writes its result into the chain as `TIME_ANCHOR` (format specification 4.22). From edition 1.10 the setup MAY suggest an authority (format specification 7.3, "Suggested authority"). For a suggested authority: neither the vendor nor a party affiliated with it (§12) operates it, and it SHOULD be run by a different operator than the time-stamping authorities of the vendor log (§9.9). Not a byte goes to it before the customer has confirmed it, and the customer can deselect or replace it at any time. The request names nothing about the installation or the customer, carries no authorisation that the vendor issues or pays for, and SHOULD carry a nonce (`nonce`) and `certReq = true`. The vendor never ships the authority's root and builds it in nowhere; the vendor's documentation names where the authority publishes it. The system's root store never counts for a time witness (format specification 7.3, 10.8).

**Duties of the vendor outside the messages (from edition 1.10).** This document also governs what the vendor MUST do independently of the three messages: close and publish the vendor log (§9.9), state the affiliation of a customer with the vendor (§9.10), keep separate keys for every role and keep them in custody (§9.11), and separate the data it holds about customers from affiliated parties and record accesses to them (§12). None of these duties adds a message, a field or a fetch to the appliance.

## 2. Principle: no free text, by construction

> **Integers, enums and fixed-length hex only; no free-text field exists by construction.**

The recurring messages `heartbeat` and `anchor` consist exclusively of integers, enum values from fixed published value lists, fixed-length hex strings and values with a fixed grammar (UUID, RFC 3339 timestamp, SemVer). A field into which free text (such as prompts, responses, user names, source names, internal addresses or configuration content) could be written is not present in the schema and therefore cannot be filled even by misoperation or a software defect. The `activation` (at commissioning, again only in the cases of §4) additionally carries length-bounded technical identifiers (the SHA-256 commitment of the license key, the proof of possession `license_proof`, key id, IANA timezone name); it too contains no field for free content. The key id is set by the installation; the server uses it only as part of the signature subject and from edition 1.10 does not keep it (§4).

This property is construction, not configuration: telemetry serializes only typed structs whose schema is frozen in CI (any new field turns CI red), and the server discards everything not in the schema (§8).

## 4. Message type `activation`

At commissioning. Registers the Ed25519 device public key against which the server verifies all later signatures.

**Renewed activation (from version 1.9).** An appliance activates again in two cases only: after the server answered `heartbeat` or `anchor` with HTTP 403 `unknown_appliance`, and after a key replacement (§4.1). A chain succession (§9.2 step 1) is a procedure at the vendor and no occasion; the activation carries no `chain_id`. Every renewed activation carries the same `appliance_id` and the same device key and is chained before sending like every message (§1). Between two activations, whatever their occasion, at least 30 seconds pass; the spacing doubles with each activation up to at most 15 minutes and starts again at 30 seconds only after an hour without an activation. That makes at most eight activations in any hour. The appliance measures the spacing with a monotonic clock; it SHOULD keep it across a restart. If it does not keep it, the first renewed activation after a restart waits the largest spacing of 15 minutes, so that a restart loop does not lift the bound.

| Field | Type | Constraint |
|---|---|---|
| `license_commitment` | hex64 | SHA-256 over the UTF-8 bytes of the license key. The key itself is never sent, never chained and never exported; the server finds the license through the commitment. The commitment is public (every verification package carries it) and proves nothing by itself |
| `license_proof` | hex64 | proof of possession of the license key (§4.1); from `spec_version` 1.8, required by the server regardless of the declared version |
| `appliance_id` | uuid | - |
| `device_pubkey` | hex64 | Ed25519 public key of the device key |
| `device_key_id` | string | maxlen 64; technical identifier of the device key without any customer information: the installation SHOULD set it to a fixed form such as `geraet-1`, never to a name, host name or address. From edition 1.10 the server uses it only as part of the signature subject (§7), does not store it, writes it into no log and does not output it; it keeps the device key by `device_pubkey` |
| `version` | semver | appliance software version |
| `spec_version` | version | specification version the appliance implements (`1.0`, `1.1`, …); steers the message contract of `anchor` (§6, §9) |
| `edition` | enum | `starter` \| `pro` \| `group` \| `enterprise` |
| `language` | enum | `de` \| `en` |
| `timezone` | string | maxlen 64 (IANA timezone name) |
| `sig` | hex128 | Ed25519 signature (§7) |

The server's response is governed by §9.3.

### 4.1 Proof of possession `license_proof`

The `license_commitment` is not secret: every verification package carries it, in the chained activation and from version 1.8 also in `GENESIS` (format specification 4.1). Presenting the commitment alone therefore proves nothing. The appliance proves possession of the license key with

`license_proof = HEX( HMAC-SHA256( K, M ) )`

- `K` is the UTF-8 bytes of the license key exactly as issued (without trimming and without case folding), i.e. the same bytes `license_commitment` is computed over.
- `M` is the ASCII bytes of the field value `device_pubkey` (64 characters) immediately followed by those of the field value `appliance_id` (36 characters), exactly as both appear in the same message: 100 bytes without a separator. Both fields have a fixed length; the concatenation is unambiguous.
- HMAC per RFC 2104 with SHA-256; `HEX` is lowercase hex encoding (64 characters).
- Reference values: `spec/contract/license_proof.json`.

The server checks an activation in this order: signature (§7) and schema (§8); the license via `license_commitment` (unknown: HTTP 403 `unknown_license`); `license_proof`, recomputed with the stored check value of the license key and compared in constant time (check value: the key itself or the two SHA-256 chaining values after the single 64-byte block `K' ⊕ ipad` and `K' ⊕ opad` respectively, where `K'` is `K` padded with zero bytes to 64 bytes (RFC 2104 step 1), not the SHA-256 value of these blocks; from them HMAC-SHA-256 is computed identically per RFC 2104 section 4; whoever holds the check value can form proofs, so it is protected like the key) (different: HTTP 403 `license_proof_invalid`, nothing is registered; if it is missing, the schema already fails: HTTP 400 `invalid_field`, field `license_proof`, before any license check; this is also what an appliance before version 1.8 gets); only then edition, appliance limit and registration. A request without a valid proof MUST NOT be counted against the license's request quota: otherwise anyone holding a verification package could use the public commitment to drive the customer's heartbeats and anchors into throttling. The server requires `license_proof` regardless of the declared `spec_version`. An older declared version is no way around the proof. Appliances already registered stay registered; the server keeps checking their heartbeats and anchors against the registered device key.

**What the proof binds.** It binds the license key to exactly one pair of device key and `appliance_id`. Whoever holds a verification package knows the commitment and the chained activation including `license_proof`, but not the key: they cannot register a device key of their own. They can only repeat the chained message verbatim. The server MUST treat a verbatim repetition (same `appliance_id`, same `device_pubkey`, same license) as already done: no new appliance, nothing counted against the appliance limit. An activation that was chained but never reached the vendor or was refused (egress off, send failure, `appliance_limit_reached`) can be submitted first by a package holder. Therefore a registered appliance counts against the appliance limit, and silence monitoring (§10) starts, only once the first valid heartbeat signed with the registered device key has arrived (from version 1.9); until then the registration is only pending. A package holder cannot sign a heartbeat. An activation for a registered `appliance_id` with a different device key stays HTTP 409 `already_registered`, even with a valid proof. From edition 1.10 this holds for every `appliance_id` that the device-key journal (§9.7) knows with a different device key, even if its registration has been removed, for instance on the replacement of a license; the answer appends to no journal. Otherwise another appliance could continue the chains of the earlier one under the same `appliance_id`, and `owner_keys` would name both keys. Replacing the device key is a procedure at the vendor, not a self-service path; it appends to the device-key journal.

**Key form and key strength.** A license key follows the grammar `^[A-Z0-9-]{19,29}$` (registry `cloud_messages.activation.license_key_grammar`): at most 29 bytes and only uppercase letters, digits and hyphen. Both matter for security: a key over 64 bytes would, per RFC 2104, be shortened with SHA-256 before the HMAC, and the result would be exactly the public commitment, from which every `license_proof` could then be computed; and a key of 64 lowercase hex characters would look like a commitment and end up in cleartext in `GENESIS` (format specification 4.1). The commitment is an unsalted SHA-256. A license key MUST therefore also carry at least 80 bits from a cryptographically secure random generator, and the vendor MUST NOT issue freely chosen keys: a weaker key can be recovered from the public commitment by trial, and with it every `license_proof`. In this version the license key serves only this proof; any future further HMAC use MUST include its own identifier in the message, so that the proofs cannot be swapped.

**Disclosed keys.** Up to version 1.7 the standard installation wrote the license key in cleartext into `GENESIS` (format specification 4.1), and a chain can never shed it. Every key that ever stood in a `GENESIS` counts as disclosed and MUST be replaced by the vendor; for a disclosed key `license_proof` proves nothing. **Replacement (specified from version 1.9):** the license stays the same (term, registrations and anchor history remain); from then on the vendor keeps the new commitment for it, and every statement (§9.4) carries it. The operator installs the new key on the appliance; the appliance activates again with it (same `appliance_id`, same device key, valid proof under the new key), and the server rebinds the registration: HTTP 200, no `already_registered`. It no longer accepts a proof under the replaced key afterwards. `GENESIS.license_id` remains the commitment at the time the chain was created (format specification 4.1).

**Acceptance of the rebinding (from version 1.9).** The appliance counts a rebinding as accepted only once the 200 answer to its activation carries both:

1. in the member `license` a license statement effective per §9.4 with the commitment of the configured, that is the new, key, whose `server_ts` deviates from the appliance's own clock by at most 15 minutes, in either direction. It shows that the vendor holds the license under the new commitment; it is not bound to any appliance;
2. in the member `activation_receipt` an activation receipt effective per §9.8 with the appliance's own `appliance_id`, its own `device_pubkey` and the same commitment, whose `server_ts` likewise deviates by at most 15 minutes. Only the receipt binds the answer to this registration: a statement alone could be taken by someone in the transport path from the answer to another appliance of the same license.

If either is missing or not effective, the rebinding has failed. The appliance repeats it with the spacing of §4 and reports the failure. Recording and anchoring do not depend on it.

**Appliance side of the replacement (from version 1.9).** An appliance considers itself registered when it has recorded an accepted activation (a rebinding only once it is accepted per the previous paragraph) or its chain carries a `CHECKPOINT_RECEIPT`; a merely chained activation does not suffice. A registered appliance keeps sending heartbeat and anchor whatever becomes of a renewed activation. With neither, the next activation is the first: if SHA-256 of the configured key differs from the commitment in `GENESIS`, it does not activate and reports the mismatch; if it cannot read the commitment from `GENESIS`, it does not activate either and reports that. If a registered appliance does not hold under which commitment its activation was accepted (activation state from a version before 1.9, or lost), `GENESIS` decides: if it names another commitment than that of the configured key, this is a key replacement; if it names the same one or cannot be read, the appliance does not activate again. While the server holds the registration only as pending (above, "What the proof binds") and the license's appliance limit is reached, it may answer heartbeats and anchors with HTTP 403 `appliance_limit_reached` (§9.5, §9.6); it then countersigns none of their anchors. The appliance then keeps sending, reports it and does not activate again because of it.

## 6. Message type `anchor`

Every 5 minutes. Carries only the Merkle root (32 bytes), the tree size and, from `spec_version` 1.1, the RFC 6962 consistency proof (node hashes of the Merkle tree). No content can be reconstructed from any of it.

| Field | Type | Constraint |
|---|---|---|
| `appliance_id` | uuid | - |
| `chain_id` | uuid | - |
| `tree_size` | int | min 1 |
| `merkle_root` | hex64 | RFC 6962 Merkle root over `tree_size` leaves |
| `consistency_proof` | object | mandatory from `spec_version` 1.1 (§9); absent from the message contract for `spec_version` 1.0 |
| `consistency_proof.from_tree_size` | int | min 0; the reference size of this chain (§9.2): the largest `tree_size` the server countersigned or recorded as a gap witness (0 = none yet) |
| `consistency_proof.hashes` | array (hex64) | RFC 6962 consistency proof from `from_tree_size` to `tree_size`; empty for `from_tree_size` 0; max 64 entries |
| `sig` | hex128 | Ed25519 signature (§7) |

## 7. Signature subject

Identical for all three message types:

1. Form the message object **without** the `sig` field.
2. Canonicalize it per RFC 8785 (JCS).
3. `sig` = Ed25519 signature over these UTF-8 JCS bytes, hex-encoded (128 characters), created with the private device key belonging to `device_pubkey`/`device_key_id` from activation (for `activation` itself: the key registered inside the message; possession of the device key is shown by the self-signature, possession of the license key by `license_proof` (§4.1), which is computed over `device_pubkey` and `appliance_id` and is therefore bound to exactly this device key).

The transport channel (plain TLS, corporate-proxy compatible) is **not** evidence-bearing; the Ed25519 signatures are. The server discards any message with an invalid signature before any further processing.

## 8. Server behaviour: strict validation

The metadata server strictly validates every incoming message against the published schema:

- **Excess fields** (top-level fields not present in the schema): the message is accepted, the excess fields are **discarded and logged** (protection also against defective future appliance versions). Discarded fields are never stored.
- **Free text in an enum position** (invalid enum value, unknown map key, pattern/grammar violation for `uuid`/`rfc3339`/`semver`/`version`/`hex`/`const`/`pattern`, over-long `array` lists): **HTTP 400**, the message is rejected in full and not stored.
- **Message contract per `spec_version`:** the server validates `anchor` against the contract of the highest `spec_version` the appliance has ever declared (activation, then every heartbeat). From 1.1 `consistency_proof` is a mandatory field; for 1.0 it does not exist in the contract and would be discarded as an excess field (§9). A **lower** `spec_version` than the one on record is not adopted; the heartbeat is accepted, the downgrade is logged and counted (`spec_version_downgrades_refused_total`): whoever holds the device key cannot reopen the contract without proof by declaring backwards.
- Range violations for `int` (`min`/`max`), missing mandatory fields, invalid signature (§7): HTTP 400 or rejection.
- **Request quota (from edition 1.9).** The server limits requests per licence. A request is counted only once it has passed every check that recognises a repetition, because every sent message stands verbatim in the verification package (§1), and whoever holds one could otherwise use genuine, validly signed messages to exhaust the customer's quota and drive its heartbeats and anchors into throttling. Not counted are: an activation without a valid `license_proof` (§4.1), a verbatim repetition of an activation, a heartbeat whose `ts` is not newer than the last one accepted from this appliance or lies outside the time window, and an anchor that §9.2 step 2 or 3 answers as a repetition or as stale. Such requests are answered without effect and limited per source at most.
- **`spec_version` 1.0** is no longer accepted by the server from edition 1.9 (§9.2, "Message contract 1.0").

Hence: even a compromised or defective appliance cannot deposit free content with the vendor over this channel; the server does not accept it.

## 9. Vendor responses

The server answers with a JSON object. Only the signed objects in it carry evidence: the countersignature (§9.1), the license statements (§9.4, §9.5) and the activation receipt (§9.8), from edition 1.10 with the pairs in `statement_signatures` (§9.3). The appliance MUST ignore response members this document does not name, and it MUST NOT derive from unsigned members any decision that concerns recording, the chain or anchoring. A narrowly bounded exception is the appliance limit at the anchor (§9.5): it decides only whether an anchor is overdue and what the status shows. No vendor statement locks, deletes or alters customer data: recording continues in every license state.

**Signed objects outside the responses (from edition 1.10).** The vendor issues two further signed objects that are not a response to the appliance and that the auditor fetches himself (§1): the pages of the anchor history (§9.7), signed with a statements key (pages of form v1 until the end of dual operation with a countersigning key), and the day entries of the vendor log (format specification 7.4, §9.9), signed with a protocol key. From edition 1.10 every key of the vendor has exactly one role (§9.11, format specification 10.7.3): a countersigning key signs countersignatures, a statements key license statements, refusal statements, activation receipts and pages of the anchor history, a manifest key only the envelope of the update manifest (§9.4) and a protocol key only day entries. During dual operation (§9.11) a countersigning key also signs the envelope (§9.4) of the three statements to the appliance and pages of form v1; the pair under a statements key then stands in `statement_signatures` (§9.3). Extracts, inclusion and absence proofs and day leaves of the log are not signed and carry no evidence of their own: they carry it only through the signed day entry whose root they prove against, and through its timestamps.

### 9.1 Countersignature

The response to a valid `anchor` message under a valid license or one in its grace period is the vendor's **countersignature** (HTTP 200):

| Field | Type | Constraint |
|---|---|---|
| `chain_id` | uuid | from the request |
| `tree_size` | int | from the request |
| `merkle_root` | hex64 | from the request |
| `server_ts` | rfc3339 | server time; from edition 1.10 exactly in the form `YYYY-MM-DDThh:mm:ss.sssZ` (§9.4 item 2) |
| `server_key_id` | string | maxlen 64 |
| `server_signature` | hex128 | Ed25519 with a countersigning key (role `countersigning`, §9.11) over JCS(`{chain_id, tree_size, merkle_root, server_ts}`) |

The appliance chains the response as a `CHECKPOINT_RECEIPT` entry. Any third party can verify the countersignature offline; it establishes the vendor public key through the vendor root published with the licence and the signed list of countersigning keys in the verification package, not through the package alone (format specification 7.1, 10.7.1); the role list never establishes a countersignature (format specification 10.7.4). The server additionally enforces per-`chain_id` **tree_size monotonicity** against the reference size (§9.2): an `anchor` with a smaller `tree_size` is not accepted; a different root at a recorded size is a fork finding, a merely stale anchor is not (§9.2 step 2).

**Issuance journal (from edition 1.10).** From edition 1.10 the server writes the `server_ts` of every countersignature exactly in the form `YYYY-MM-DDThh:mm:ss.sssZ`, like the instants of a statement (§9.4 item 2); so receipt and leaf of the vendor log are equal character for character, for the earliest countersignature of a root also the row of the anchor history (format specification 7.4.2, §9.7). The server MUST durably record every countersignature that leaves it before it answers, with exactly the signed `server_ts` (issuance journal), including a freshly issued repetition whose original it cannot deliver byte for byte. The journal is only appended to, never changed. From it the vendor forms the leaves of the vendor log (format specification 7.4, §9.9): the leaf of a countersignature is

```
UTF-8(JCS({ "chain_id": …, "merkle_root": …, "server_ts": …, "tree_size": … }))
```

that is exactly the bytes `server_signature` is computed over, with `server_ts` byte-identical to the countersignature the appliance chains. If on a repetition (§9.2 steps 2 and 3) the server delivers a recorded countersignature of this root byte for byte, the original or a repetition recorded in the journal, this is the same leaf; if it issues a new countersignature with a new `server_ts`, that is a further leaf on the day of its `server_ts`. If it cannot deliver a recorded countersignature of this root byte for byte, for instance after a change of the countersigning key, it issues a new one with a new `server_ts` and records it before the answer (on a closed day HTTP 503 `log_day_closed`); it never signs the `server_ts` of a recorded countersignature anew with another key. The anchor history (§9.7) still names for a root the time at which the server first recorded it. Without the journal a countersignature the customer holds would be missing from the log without the vendor having left it out; the verifier would then report `RECEIPT_NOT_LOGGED` (exit 1, format specification 7.4) against an honest package.

For a log day already closed the server issues no countersignature (temporary error and alarm). A day is closed as soon as its closing has begun to read its leaves (§9.9). If the `server_ts` of a new countersignature would fall on such a day, for instance after the server clock jumped backwards, the server answers with HTTP 503 `log_day_closed` (§9.6), which the appliance treats like any other failure (the anchor stays due), and raises an alarm.

### 9.2 Consistency proof and gap witness

**Consistency proof (from `spec_version` 1.1).** Monotonicity alone does not prove that the new root extends the old one: a rewritten chain that merely *grew* would pass it. Therefore the server accepts a larger `tree_size` only when `consistency_proof` proves the extension (RFC 6962 consistency proof between `from_tree_size` and `tree_size`).

**Recorded roots and reference size.** For each chain the server records every root it has checked and accepted, countersigned (§9.1) or as a gap witness (below), with `tree_size`, `merkle_root` and server time; from edition 1.9 it MUST keep all of them (anchor history, §9.7). The largest of them is the reference size `B` with its root; while there is none, `B = 0`. An anchor is checked in this order:

1. Signature (§7), schema (§8) and whether the chain belongs to the sending appliance. From edition 1.9 additionally: if the server already keeps another chain with `B > 0` for this appliance, it records nothing for a new `chain_id` until a chain succession has been registered at the vendor (a procedure at the vendor like replacing the device key, §4.1; registered are the predecessor and the `tree_size` handed over): HTTP 409 `chain_succession_required`. Otherwise whoever holds the device key could let a rewritten history begin as a new chain at `B = 0` without any proof.
2. `tree_size < B`: if a root is recorded for exactly this `tree_size` and equals the one presented, the anchor is a repetition: for a countersigned one the server answers with a recorded countersignature of this root (§9.1), for a gap witness with HTTP 409 `stale_anchor`; no finding. If a different root is recorded, the device key has signed two roots of the same size: HTTP 409 `fork_detected`, fork finding. If none is recorded for this size: HTTP 409 `stale_anchor`, no finding, nothing is recorded. A stale anchor (one chained during a network outage and never delivered, one that overtakes the resend of a newer one, or one from a verification package, where every sent anchor stands verbatim) proves no fork without a consistency proof to the reference size. The server counts such anchors (`anchors_stale_total`).
3. `tree_size = B`: with the same root the anchor is a repetition: for a countersigned `B` the server answers with a recorded countersignature of this root (§9.1), for a witnessed `B` it continues with step 5 (after a renewal the gap witness is countersigned there); with a different root it is a fork (HTTP 409 `fork_detected`, fork finding).
4. `tree_size > B`: `from_tree_size` MUST equal `B`, otherwise the server answers HTTP 409 `consistency_required` with `expected_from_tree_size = B`; the appliance fetches the matching proof from its chain and resends the anchor once. If the proof does not hold against the root at `B` and the new root, it answers HTTP 409 `consistency_failed`, accepts nothing and records a fork finding (alarm via the sweep, history in the anchor history). With `B = 0`, `hashes` is empty: the first recorded root of a chain needs no proof.
5. Only now the license: valid or in grace → countersignature (§9.1); expired → gap witness and refusal (§9.5).

The license check comes after the consistency check. So even an anchor the server does not countersign has been checked, and a fork during a license lapse is detected like any other.

**Gap witness.** If the server refuses to countersign an anchor that passed steps 1 to 4 because the license has expired, it MUST durably record that anchor's `tree_size` and `merkle_root` as a **gap witness** of this chain before it answers; from then on they are the reference size `B`. Every later anchor of the chain, during the lapse and after a renewal, must therefore prove that it extends exactly this root. A gap witness is not a countersignature and is never delivered as one; the anchor history (§9.7) names it as what it is.

**Gap witness in the vendor log (from edition 1.10).** Every gap witness is a leaf of the vendor log (format specification 7.4, §9.9). Its subject is exactly

```
UTF-8(JCS({ "chain_id": …, "kind": "ledger.vendor_log_gap_witness.v1", "merkle_root": …, "server_ts": …, "tree_size": … }))
```

(canonical order as written). `chain_id`, `tree_size` and `merkle_root` are those of the recorded anchor; `server_ts` is the time at which the server first recorded the gap witness, from edition 1.10 in the form `YYYY-MM-DDThh:mm:ss.sssZ`, exactly the stored character string that the anchor history names in the row `gap_witness` of this root (§9.7), never reformatted and not the time of a later anchor of the same root. Per root (`chain_id`, `tree_size`, `merkle_root`) the server records at most one gap witness. The first refusal statement for this anchor carries exactly this character string as `server_ts`, every later one its own time of issue (§9.5). The leaf belongs to the day of this `server_ts`. It carries no `appliance_id`, no commitment and no refusal statement; no statement enters a leaf (§9.5). It is not signed by itself: the vendor commits to the set of a day's leaves with the signed day entry. The member `kind` distinguishes the leaf from every leaf of a countersignature with the same values, since the subject of the latter has exactly the four members of §9.1 without `kind`. If the server later countersigns the same root (step 3, after a renewal), a second leaf arises, that of the countersignature, on the day of its `server_ts`; the leaf of the gap witness remains.

**Reported roots (from edition 1.9).** In addition the server MUST record every device-signed root that reaches it without being accepted: the `last_checkpoint` of every valid heartbeat (§5) and the root of every anchor it answers with `consistency_required`. They are not a reference size (unchecked, they prove no extension), but they stand in the anchor history as reported roots: the appliance itself declared at that time that its chain had this root. From edition 1.10 the server records a reported root only if it has bound its `chain_id` to the sending appliance (the same check as step 1 above); for a `chain_id` it has bound to no appliance or to another one it records nothing, and a heartbeat binds no chain. If an appliance presents in a valid heartbeat a `chain_id` that the server has bound to no appliance, the server MAY reserve it for this appliance (claim): it then answers the anchor of another appliance for this `chain_id` with HTTP 403 `chain_owner_mismatch`. A claim is no binding: it makes no reported root recordable, and until it is bound the chain stays unknown (§9.7). Reference case: `spec/contract/gemeldete_wurzeln.json`. Otherwise anyone who operates a licensed appliance of their own and knows a foreign `chain_id` could slip a root into the anchor history of this chain. The verifier in any case never judges a root that is only reported and contradicts the package as `MERKLE_INCONSISTENT`, but as `ANCHOR_HISTORY_FORK` (exit 1, format specification 8.8.5).

What this closes: without gap witnesses the first anchor after a renewal only had to prove that it extends the last root BEFORE the lapse. Whoever holds the device key and the chain files could until then rewrite every entry from the lapse, rebuild the Merkle tree and have the rewritten version countersigned. With gap witnesses this reaches back, as in licensed operation, only to the latest recorded root (residual window, format specification 11.2); a rewrite before it fails the consistency proof and is reported as a fork, and in a verification package it shows in the comparison with the anchor history (§9.7). **Limit:** whoever keeps the anchors from reaching the vendor during the lapse prevents gap witnesses; he loses no receipts by it, since there are none during a lapse. As long as the heartbeats get through, their reported roots are recorded, and the anchor history shows heartbeats without an accepted anchor. If he blocks the heartbeats too, the vendor reports the silence (§10), and the anchor history ends before the lapse; the verification package shows the residual window over the whole period (format specification 11.2).

**Choice of `from_tree_size`.** The appliance SHOULD use as `from_tree_size` the latest `tree_size` the vendor countersigned for this chain (§9.1) or confirmed in an effective refusal statement (§9.5); the resend after `consistency_required` remains the fallback.

**Message contract 1.0 (ended from edition 1.9).** Up to edition 1.8 appliances with `spec_version` 1.0 had a message contract without `consistency_proof`. It has ended: whoever activates a new appliance declaring 1.0 could have its anchors recorded without any proof. From edition 1.9 the server accepts no activation and no heartbeat with `spec_version` 1.0 (HTTP 400 `invalid_field`, field `spec_version`) and no anchor without `consistency_proof`.

### 9.3 Responses at a glance

| Request | HTTP | Response |
|---|---|---|
| `activation` | 200 | `{"status": "activated", "customer_id": <string>, "license": <license statement §9.4>, "activation_receipt": <activation receipt §9.8>, "statement_signatures": <pairs under statements keys, below>}`, also for an expired license; the statement then says `expired` |
| `heartbeat` | 200 | `{"status": "ok", "license": <license statement §9.4>, "update": <update notice, below>, "update_arch": <checksums per architecture, below>, "statement_signatures": <pairs under statements keys, below>}`; `license` is absent when the server cannot issue a statement, `update` when no update is announced; `update_arch` is present exactly when `update` is |
| `anchor` | 200 | countersignature (§9.1) |
| `anchor` | 403 | refusal because the license expired (§9.5), with `statement_signatures` |
| any | 4xx, 503 | error response (§9.6) |

**Pairs under statements keys `statement_signatures` (from edition 1.10).** The member `statement_signatures` (registry `cloud_response_members.statement_signatures`) carries for every statement of the same response a second pair of key and signature, under a statements key (§9.11): for `license` in the 200 responses to `activation` and `heartbeat` and in the 403 response `license_expired` (§9.5), for `activation_receipt` in the 200 response to `activation` (§9.8). It is an object with one member per such statement, named like that statement's member (`license`, `activation_receipt`). Each has exactly the members `server_key_id` (string, `^[A-Za-z0-9._-]{1,64}$`) and `server_signature` (hex128): Ed25519 by a statements key over the UTF-8 bytes of that statement's `statement_jcs`. The envelope of the statement (§9.4) keeps its four members. Until the end of dual operation (§9.11) a countersigning key signs the envelope, and the server MUST send `statement_signatures` along; afterwards a statements key signs the envelope, and `statement_signatures` MAY be absent. A recipient of edition 1.9 does not know the member and ignores it (§9). A recipient of edition 1.10 accepts both forms and deals with faulty data as follows:

- If `statement_signatures` is not an object, or if one of its members is not an object of exactly these two strings in their grammar, it ignores this pair and judges the statement by the remaining pairs (§9.4 item 3).
- It ignores a member that names no statement of the response.
- A response with duplicate member names anywhere is not I-JSON; it is an ordinary failure.

Reference cases: `spec/contract/statement_signatures.json`.

**Update notice (from edition 1.9).** The member `update` of the heartbeat response announces an update (registry `cloud_response_members.update`):

| Member | Type | Meaning |
|---|---|---|
| `version` | string, `^[0-9]+\.[0-9]+\.[0-9]+$` | announced software version |
| `channel` | string, `^[a-z]{1,16}$` | delivery channel |
| `min_version` | string, `^[0-9]+\.[0-9]+\.[0-9]+$` | lowest version the bundle can be installed from |
| `release_ts` | rfc3339 | release time, form as in §9.4 item 2 (three fractional digits, `Z`) |
| `sha256` | hex64 | SHA-256 over the whole bundle |

The notice is **unsigned** and only a notice. It is neither a trust anchor nor an order: on its account the appliance MUST NOT install anything without checking the bundle against the pinned update key (§1), obtaining the customer's consent and refusing a downgrade. A forged or altered notice can therefore only name a version that does not exist or one that is validly signed anyway, or withdraw an announcement. If `update` is absent, nothing is announced; a notice that does not match the table is discarded and the previous state kept. Which updates the vendor announces and delivers depends on the licence: security fixes always, feature updates only with an active licence (decision of 29.09.2026); the vendor decides this, not the appliance. A notice changes nothing about recording.

**Checksums per architecture (from edition 1.9, addition of 2026-10-07).** Each version has one bundle per architecture. The member `update_arch` of the heartbeat response names their checksums (registry `cloud_response_members.update_arch`):

| Member | Type | Meaning |
|---|---|---|
| `amd64` | hex64 | SHA-256 over the whole bundle for amd64 (x86_64) |
| `arm64` | hex64 | SHA-256 over the whole bundle for arm64 (aarch64) |

`update_arch` has exactly these two members and is present in the response exactly when `update` is. `update` keeps its five members; its `sha256` names the amd64 bundle. The appliance takes `update_arch` only together with `update`. If `update_arch` is present without `update` or does not match the table, it discards the whole notice like a malformed `update` and keeps the previous state. The updater fetches the bundle of its own architecture, `<source>/<version>/ledger-<version>-<architecture>.rbundle`, and checks it against that architecture's checksum. If `update_arch` or its own architecture in it is missing, it fetches nothing. Everything said above about the notice applies to `update_arch`: unsigned, not a trust anchor, the checksum protects the transport only, the signature against the pinned update key stays mandatory (§1). The bundle's signed manifest does not change. Someone who alters both the notice and the source can slip an appliance a validly signed bundle of the other architecture; the signature alone does not rule that out.

### 9.4 License statement

A statement travels in the response member `license`, as an object with exactly these four members (registry `cloud_statements`):

| Member | Type | Meaning |
|---|---|---|
| `statement_jcs` | string | the statement in JCS form (RFC 8785); only these bytes are signed |
| `server_key_id` | string, `^[A-Za-z0-9._-]{1,64}$` | identifier of the signing key (format specification 10.7.3): for license statements, refusal statements, activation receipts and pages of form v1 a countersigning key until the end of dual operation, a statements key afterwards; for pages of form v2 always a statements key (§9.11) |
| `server_signature` | hex128 | Ed25519 over the UTF-8 bytes of `statement_jcs` |
| `statement` | object | unsigned reading copy of `statement_jcs`; the recipient MUST ignore it |

`statement_jcs` is at most 2048 characters long (registry `cloud_statements.wrapper_fields`). From edition 1.10 there is one exception: a page of the anchor history of kind `ledger.anchor_history.v2` may be up to 131 072 characters long (§9.7); it consists of printable ASCII characters only, so characters and bytes are equal in number there. For every other kind the limit stays 2048, also for pages of kind `ledger.anchor_history.v1`. An appliance reads no page of the anchor history; no limit changes for it.

The statement `ledger.license_statement.v1` has exactly these members:

| Member | Type | Meaning |
|---|---|---|
| `kind` | const `"ledger.license_statement.v1"` | kind of statement |
| `license_commitment` | hex64 | commitment of the license (§4) |
| `state` | enum `valid` \| `grace` \| `expired` | license state at `server_ts` |
| `countersigning` | bool | whether the vendor countersigns anchors under this license; `true` exactly when `state` is not `expired` |
| `updates` | bool | whether the license entitles to feature updates; in this version equal to `countersigning`. Security fixes do not depend on it (decision of 29.09.2026) |
| `server_ts` | rfc3339 | time of issue by the server clock |
| `valid_until` | rfc3339 or `null` | end of the term; `null` for a license without a term |
| `grace_until` | rfc3339 or `null` | end of the grace period; `null` for a license without a term |

A statement is effective only if the recipient (appliance, portal) confirms ALL of the following:

1. `statement_jcs` is I-JSON without duplicate member names and exactly the JCS form of its own content: canonicalized again, it yields the same bytes.
2. The members are exactly those of the table, with the stated types; instants have exactly the form `YYYY-MM-DDThh:mm:ss.sssZ`: UTC, three fractional digits, `Z`, as in format specification 10.7 (stricter than §3, which allows any RFC 3339 UTC time for requests); `kind` is the expected kind.
3. Key and signature hold. A pair is a key `server_key_id` with a signature `server_signature` over the UTF-8 bytes of `statement_jcs`.
   - A recipient of edition 1.9 checks the pair of the envelope: `server_key_id` is valid at `server_ts`, per the signed list of countersigning keys (format specification 10.7.1) or as a key pinned at installation, and `server_signature` holds.
   - A recipient of edition 1.10 checks the pair of the envelope and the pair in `statement_signatures` (§9.3). At least one of them names a key of role `statements` that is valid at `server_ts`, per its role list (format specification 10.7.2) or as a statements key pinned at installation, and its signature holds. A pair under a key of another role never counts, not even as a fallback.
4. `license_commitment` is the recipient's own commitment: that of the license key installed on the appliance, not `GENESIS.license_id`, which differs after a key replacement (§4.1).
5. For `ledger.license_statement.v1` only: `countersigning` is `true` exactly when `state` is not `expired`; a contradiction makes the statement ineffective.
6. `server_ts` lies at most 15 minutes after the recipient's own clock.

The recipient never replaces an effective statement it holds by one with an older `server_ts`; so nobody can replay an old, more favourable statement, not even with a meanwhile revoked key that was valid at its time. If the latest effective statement is more than three hours (three heartbeats) old, the recipient shows it as stale.

An ineffective statement is no information; it changes nothing. An effective statement is for display (portal, telemetry status) and does not change recording either. Up to edition 1.9 the same key signed countersignatures and statements; from edition 1.10 every role has keys of its own (§9.11). During dual operation a countersigning key still signs the envelope of the statements to the appliance; even then countersignature and statement cannot be confused: the signature subject of a countersignature is JCS over exactly four members without `kind`, and every statement, every activation receipt (§9.8) and every page of the anchor history (§9.7) carries `kind`, provided the server signs nothing else with a countersigning key (§9.11 item 3). A verifier does not evaluate statements; from edition 1.10 it reads pages of the anchor history in form v2 as an auditor input (§9.7, format specification 8.8). Reference values with a test key: `spec/contract/license_statement.json`.

**Update manifest (from edition 1.10).** The vendor signs the update manifest (`GET /v1/update-manifest`) only with a manifest key (role `update_manifest`, §9.11) and only inside an envelope with `kind`. The signature subject is

```
UTF-8(JCS({ "kind": "ledger.update_manifest.v1", "manifest": <object> }))
```

with the manifest as `<object>`. No running service holds the manifest key: the vendor signs the envelope at release, and the server delivers the stored signature. The envelope is stored as a JSON object with exactly the members `statement_jcs` (string: the envelope in JCS form, I-JSON without duplicate member names; only these bytes are signed), `server_key_id` (string, `^[A-Za-z0-9._-]{1,64}$`: the `key_id` of the manifest key) and `server_signature` (hex128: Ed25519 over the UTF-8 bytes of `statement_jcs`), like `entry` in §9.9 and without a reading copy; `GET /v1/update-manifest` answers with exactly the stored bytes. Before every delivery the server checks: `statement_jcs` is the JCS form of an object with exactly the members `kind` and `manifest`, `kind` is `ledger.update_manifest.v1`, `manifest` is an object without a member `kind` and not with exactly the four members of §9.1, and the signature holds under a key that the role list the server goes by (§9.11 item 6) names as valid with role `update_manifest` at the time of the request. No server signs a configured manifest with a countersigning key, in any phase; as long as no envelope signed with a manifest key is available, the server hands out no update manifest (HTTP 404 `no_manifest`), and it never hands out a stored envelope that fails the check (HTTP 503 `manifest_unavailable` and an alarm, §9.6). The vendor does not sign a manifest that itself carries a member `kind` or exactly the four members of §9.1 (`chain_id`, `merkle_root`, `server_ts`, `tree_size`). So no object that a key of the vendor signs has the signature subject of another: a countersignature has exactly the four members without `kind`, every other object a `kind` with the value of its kind, and every role has keys of its own (§9.11).

### 9.5 Refusal because the license expired

If the license has expired (after its term and grace period), the server answers an anchor that passed §9.2 steps 1 to 4, after storing the gap witness, with HTTP 403:

| Member | Type | Meaning |
|---|---|---|
| `error` | const `"license_expired"` | error code (§9.6) |
| `detail` | string | explanation; not evaluated |
| `valid_until`, `grace_until` | rfc3339 or `null` | unsigned copies; not evaluated |
| `license` | object | object per §9.4 with a refusal statement `ledger.anchor_refusal.v1` |
| `statement_signatures` | object | from edition 1.10: pair under a statements key for `license` (§9.3) |

The refusal statement has exactly these members:

| Member | Type | Meaning |
|---|---|---|
| `kind` | const `"ledger.anchor_refusal.v1"` | kind of statement |
| `license_commitment` | hex64 | commitment of the license (§4) |
| `appliance_id` | uuid | from the request |
| `chain_id` | uuid | from the request |
| `tree_size` | int, min 1 | from the request |
| `merkle_root` | hex64 | from the request |
| `server_ts` | rfc3339 | time of issue by the server clock |
| `valid_until` | rfc3339 or `null` | end of the term |
| `grace_until` | rfc3339 or `null` | end of the grace period |

It states: the vendor checked the anchor (`chain_id`, `tree_size`, `merkle_root`) of appliance `appliance_id` at `server_ts` and recorded it as a gap witness (§9.2), and it does not countersign it because the license has expired. It is not a countersignature: the appliance MUST NOT chain it as a `CHECKPOINT_RECEIPT`, and a verifier does not count it as an anchor. It is, however, a vendor-signed statement about this root at `server_ts`: whoever keeps it can present it to an auditor, who can check the root like a gap witness as an expected root (format specification 11.2). That such a transferable statement arises after the licence has expired is intended: it is the gap witness in the customer's hands. From edition 1.10 whoever keeps it also keeps the pair from `statement_signatures`. An auditor following edition 1.10 passes the root of a kept refusal statement as an expected root only if a pair under a statements key holds (§9.3 `statement_signatures`, after the end of dual operation the envelope); otherwise he takes the row `gap_witness` of the anchor history of form v2 (§9.7).

The appliance MUST treat a 403 response to an anchor as a license lock only if ALL of the following hold:

1. `error` is `license_expired`, and `license` is present.
2. The statement is effective per §9.4 items 1 to 4 (item 3 in the form for the recipient's edition), with `kind` = `ledger.anchor_refusal.v1`.
3. `appliance_id` is its own; `chain_id`, `tree_size` and `merkle_root` are exactly those of the anchor this request sent.
4. `server_ts` deviates from its own clock by at most 15 minutes.

Then the anchor counts as answered (it is not overdue), the telemetry status shows the lock, and the appliance MAY use `tree_size` as the next `from_tree_size` (§9.2). If anything does not hold, the response is an ordinary failure: the anchor stays due and is reported as missing under the telemetry's rules.

**Exception: appliance limit at the anchor (from version 1.9, addition of 2026-10-05).** A 403 `appliance_limit_reached` to an anchor is not a failure while the appliance's registration can still be only pending, that is while the server answers its heartbeat itself with `appliance_limit_reached` or has not taken any of its heartbeats since the telemetry started (§4.1). The anchor is then not overdue, the appliance chains nothing as `CHECKPOINT_RECEIPT`, keeps sending at its usual cadence and reports the state. Once the server has taken a heartbeat since the start and did not refuse the last one it answered with `appliance_limit_reached`, the registration is confirmed; the same answer to an anchor is then an ordinary failure. The state ends with any other answer of the server, including a 200 whose countersignature does not hold, but not with a transport error. The 403 is not signed. It therefore decides only whether the anchor is overdue and what the status shows, never anything about the chain or a receipt. In this state the appliance never reports `green` for `telemetrie`. Someone on the transport path can fake the state and hold it as long as the server takes no heartbeat; it stays visible while they do.

What the binding closes: a captured statement fits only the anchor it answered. Whoever sits in the transport path (for instance a TLS-intercepting corporate proxy) cannot produce a statement for a new root, and can replay an old one only for exactly the anchor it already fitted. An unbound statement, however fresh, would have made every anchor of a 15-minute window appear "answered" while no root reached the vendor (precisely the roots §9.2 needs as gap witnesses). The freshness check in item 4 additionally limits replaying the same anchor. Reference cases: `spec/contract/anchor_refusal.json`, sequence with gap witnesses: `spec/contract/lueckenzeuge.json`.

| 503 | `log_day_closed` | the log day of the `server_ts` is already closed (§9.1, §9.9); temporary, the anchor stays due; SHOULD NOT count against the request quota (§9.9, "Issuance", item 4) | - |
| 503 | `signing_unavailable` | the server currently issues no signature: the key it would go out under is not valid at the `server_ts` by the vendor's lists, or the service holding it does not sign (§9.11 items 4 and 6); temporary, the anchor stays due, nothing is recorded for it; never on a heartbeat, where `license` is absent instead (§9.3) | - |
| 503 | `anchor_history_v2_unavailable` | the server does not yet hand out pages of form v2 (§9.7, obligation 10) | - |
| 503 | `anchor_history_read_slow` | the read for a page of form v2 took longer than 20 seconds (§9.7, obligation 5) | - |
| 503 | `server_clock_behind` | a recorded time of the page would lie after the server clock (§9.7, obligation 5); alarm | - |
| 503 | `manifest_unavailable` | update manifest: the stored envelope fails the check of the server (§9.4); nothing is delivered; alarm | - |

`countersigned_maximum` carries the reference size `B`; the name dates from version 1.1 and from version 1.8 includes gap witnesses. An answer with HTTP 429, 500 or 503 to a fetch of the anchor history is, for the auditor, no information about the package; they fetch again later (§9.7, "Fetch by the auditor", item 2).

### 9.7 Anchor history

The server hands out the **anchor history** of every chain (normative from edition 1.9): all recorded and reported roots (§9.2), signed like a statement (§9.4). It is fetched without login by the `chain_id`; the `chain_id` stands in every verification package and cannot be guessed. From edition 1.10 it exists in two forms: v1 with `kind` = `ledger.anchor_history.v1` (registry `cloud_statements.anchor_history`) and v2 with `kind` = `ledger.anchor_history.v2` (registry `cloud_statements.anchor_history_v2`). The history holds no names, no contact data, no `appliance_id` and no commitment in cleartext; if a customer of the chain is a natural person, the affiliation statement (§9.10), for instance `key_management`, is a statement about this person that anyone who knows the `chain_id` can fetch; the `owner_keys` of form v2 are hash values (below). If the server does not know the chain (no accepted anchor and no registered chain succession), it answers HTTP 404 `unknown_chain` in both forms.

**Form v1.** `GET /v1/anchors?chain_id=<uuid>`, optionally `&since_tree_size=<n>`, without the parameter `kind`. From edition 1.10 the server delivers this form unchanged and, until the end of dual operation (§9.11), under a countersigning key, that is byte for byte as in edition 1.9, so that existing tools and procedures keep working; afterwards a statements key signs it. The page has exactly these members:

| Member | Type | Meaning |
|---|---|---|
| `kind` | const `"ledger.anchor_history.v1"` | kind of statement |
| `chain_id` | uuid | the chain |
| `predecessor` | object or `null` | registered chain succession (§9.2 step 1): `chain_id` of the predecessor chain and the `tree_size` handed over there |
| `successor` | object or `null` | registered successor: its `chain_id` and the `tree_size` handed over from this chain |
| `reference_tree_size` | int, min 0 | the reference size `B` |
| `roots` | array | per root: `tree_size`, `merkle_root`, `recorded_as` (`countersigned` \| `gap_witness` \| `reported`), `server_ts`; ascending by `tree_size`, for equal sizes by time |
| `forks` | array | per fork finding: `tree_size`, `merkle_root`, `detected_ts` |
| `since_tree_size` | int, min 0 | from the request; only roots from this size on |
| `truncated` | bool | `true`: more roots follow; the next request sets `since_tree_size` higher |
| `server_ts` | rfc3339 | time of issue by the server clock |

**Form v2 (from edition 1.10).** `GET /v1/anchors?chain_id=<uuid>&kind=ledger.anchor_history.v2`, optionally `&since_tree_size=<n>`. Every response is a page: an object per §9.4 (`statement_jcs`, `server_key_id`, `server_signature`, `statement`), signed with the statements key `server_key_id` (role `statements`, §9.11; format specification 8.8.3), Ed25519 (RFC 8032, without context and without prehash) over the UTF-8 bytes of `statement_jcs`. `statement_jcs` is the JCS form of the page, consists of printable ASCII characters only (0x20 to 0x7E) and is at most 131 072 characters long (§9.4); `statement` is the unsigned reading copy, which the recipient ignores. The page has exactly these members, all present, no others:

| Member | Type | Meaning |
|---|---|---|
| `kind` | const `"ledger.anchor_history.v2"` | kind of the page |
| `chain_id` | uuid | the chain |
| `owner_keys` | array, 1 to 16 × hex64, strictly ascending | owner commitments: one hash value per device key of the appliance the chain belongs to (below) |
| `predecessor` | object or `null` | registered chain succession as in v1: `chain_id` of the predecessor chain and the `tree_size` handed over there (int, min 1) |
| `successor` | object or `null` | registered successor as in v1: its `chain_id` and the `tree_size` handed over from this chain (int, min 1) |
| `reference_tree_size` | int, min 0 | the reference size `B` |
| `roots` | array, 0 to 500 | per root in the range of the page: `tree_size` (int, min 1), `merkle_root` (hex64), `recorded_as` (`countersigned` \| `gap_witness` \| `reported`), `server_ts` (rfc3339, the stored character string, duty 6 below) |
| `forks` | array, 0 to 500 | per fork finding in the range of the page: `tree_size` (int, min 1), `merkle_root` (hex64), `detected_ts` (rfc3339) |
| `forks_omitted` | int, min 0 | number of fork findings in the range of the page that it does not list (signed omission marker) |
| `since_tree_size` | int, min 0 | from the request; lower bound of the range of the page |
| `next_since_tree_size` | int, min 1, or `null` | `since_tree_size` of the next page and at the same time upper bound of the range of this page (exclusive); `null` exactly when `truncated` is `false` |
| `truncated` | bool | `true`: further tree sizes follow on the next page |
| `affiliation` | object | affiliation of the customer with the vendor per §9.10, as of `server_ts`: `known_since` (rfc3339 or `null`) and `periods` (array, 0 to 16), per period `bases` (array, 1 to 8 codes from §9.10, strictly ascending), `from` (rfc3339), `until` (rfc3339 or `null`), `recorded_ts` (rfc3339), `merged` (bool) |
| `server_ts` | rfc3339 | time of issue by the server clock, taken after all reads for the page |

The range of a page is the tree sizes from `since_tree_size` on and, if `next_since_tree_size` is not `null`, below `next_since_tree_size`. All instants have exactly the form `YYYY-MM-DDThh:mm:ss.sssZ` (§9.4 item 2), except `server_ts` in `roots`: it is the stored character string of the countersignature or recording (duty 6), from edition 1.10 in the same form (§9.1, §9.2), for a root recorded earlier as the server wrote it then, in any case of type `rfc3339` of format specification 2. The page rules compare instants in whole milliseconds (format specification 2). All numbers lie within the number rule of format specification 2 (at most 2^53−1). JCS order of the members: `affiliation, chain_id, forks, forks_omitted, kind, next_since_tree_size, owner_keys, predecessor, reference_tree_size, roots, server_ts, since_tree_size, successor, truncated`; in `affiliation`: `known_since, periods`; in a period: `bases, from, merged, recorded_ts, until`. The limit of 131 072 characters and 500 roots per page applies to this kind only.

**Page rules.** Every page of form v2 keeps all of these rules. If a page whose signature holds violates one of them, the verifier reports `ANCHOR_HISTORY_CONTRADICTION` (exit 1, format specification 8.8): the key has then signed a page that breaks the rules.

1. `next_since_tree_size` is `null` exactly when `truncated` is `false`; otherwise it is larger than `since_tree_size` and larger than every `tree_size` of the page.
2. Every `tree_size` in `roots` and `forks` lies in the range of the page.
3. `roots` is strictly ascending by `tree_size`, then `server_ts`, then `recorded_as` in the order `countersigned`, `gap_witness`, `reported`, then `merkle_root`, and pairwise distinct by (`tree_size`, `merkle_root`, `recorded_as`).
4. `forks` is strictly ascending by `tree_size`, then `detected_ts`, then `merkle_root`, and pairwise distinct by (`tree_size`, `merkle_root`).
5. No `server_ts` of a root and no `detected_ts` lies after the `server_ts` of the page.
6. `reference_tree_size` is at least as large as every `tree_size` of a root of the page with `recorded_as` `countersigned` or `gap_witness`.
7. `predecessor.chain_id` and `successor.chain_id` differ from `chain_id` and from each other.
8. `owner_keys` is strictly ascending (lowercase hex) and has 1 to 16 entries.
9. `known_since`, if not `null`, does not lie after `server_ts`.
10. Periods: `bases` is not empty, strictly ascending and contains only codes from §9.10; `from` lies before `server_ts`; `recorded_ts` does not lie after `server_ts`; if `until` is not `null`, it lies after `from` and not after `server_ts`; only the last period MAY have `until = null`; the periods are ordered by `from` and do not overlap (the `until` of a period does not lie after the `from` of the next); if two periods adjoin, their `bases` differ.

**Owner commitment.** An entry in `owner_keys` is

```
Hex(SHA-256(UTF-8(JCS({ "appliance_id": A, "chain_id": C, "device_pubkey": K, "kind": "ledger.anchor_history.owner.v1" }))))
```

(canonical order as written, lowercase hex). `A` is the `appliance_id` of the appliance the chain belongs to: the one to which the server bound the chain (§9.2 step 1), or, for a chain it knows only through a registered chain succession, the appliance of that succession. `C` is the `chain_id` of the page, `K` a device key (hex64) the server has registered for `A`. For this, from edition 1.10 the server MUST record every device key it registers for an appliance, with the time of registration, and never delete it (device-key journal); at the changeover it takes over the key registered at that time. `owner_keys` names one commitment per recorded key. If the server cannot name any device key of the appliance, it hands out no page with an empty list; it answers HTTP 409 `owner_key_unknown` and raises an alarm. The device-key journal names at most 16 keys for an appliance: the vendor carries out no further change of the device key; the appliance is then activated under a new `appliance_id` and begins a new chain. If the journal nevertheless names more than 16, the server hands out no page; it answers HTTP 500 `owner_keys_exceeded` and raises an alarm. Reference value: for the test vector `valid_sealed_export` (`appliance_id` `de431f78-75fd-49ae-b4bf-1cb543b635d1`, `chain_id` `3cef4d7e-4d65-41d6-912d-90d51fda8982`, `device_pubkey` `da78e8f07243904c3669c59bded1b62bc1ad39b520d17d0834f4f77aa892073b`) the commitment is `d0184bb5619fab41289c330c51c12d3353538b46f852fcfb31ef9b2f83a92a28`.

What the binding closes: the server binds a chain to the appliance whose root for this `chain_id` it records first (countersigned or as gap witness, §9.2), or, through a registered chain succession, to the appliance of that succession; a claim from a heartbeat does not bind (§9.2). Whoever knows the `chain_id` of a never-anchored chain from a verification package and operates a licensed appliance of their own can anchor it beforehand; the vendor then signs a history with the roots of this other appliance. The verifier uses a page only if one of its commitments matches a device key of the package (`GENESIS.device_pubkey` or a key from `KEY_ROTATION` legitimated per format specification 6.4; format specification 8.8); otherwise it reports `ANCHOR_HISTORY_UNVERIFIED` (exit 1). So an honest package does not receive a `MERKLE_INCONSISTENT` from roots of another appliance, as long as the other appliance bound the chain. If instead the appliance of the package bound the chain, the pages are usable; another appliance can then slip only reported roots into them if a server, contrary to §9.2, records them from its heartbeats, and even then such a root yields only `ANCHOR_HISTORY_FORK` (exit 1, format specification 8.8.5). A commitment cannot be computed from the `chain_id` alone; whoever holds the package recomputes it. Because `chain_id` is part of the subject, two chains of the same appliance cannot be linked through this member.

**Server duties for form v2.**

1. Without the parameter `kind` the server delivers form v1 byte for byte as before. With a value of `kind` other than `ledger.anchor_history.v2` it answers HTTP 400 `invalid_field` with `field` = `kind`. It answers an unknown chain with HTTP 404 `unknown_chain` as in v1.
2. A page contains whole tree sizes only: all roots and fork findings of one `tree_size` stand on the same page. It contains at most 500 roots, at most 500 fork findings and at most 131 072 characters, and MAY contain fewer. If further tree sizes follow, `next_since_tree_size` is the largest `tree_size` of the page plus 1.
3. Fork findings in the range of the page that no longer fit on the page are counted by the server in `forks_omitted`; it MUST NOT silently leave out any.
4. Every page carries the complete member `affiliation` (§9.10) and the complete `owner_keys` of the chain, as of `server_ts`.
5. The server takes `server_ts` after it has read roots, fork findings, affiliation register, declarations (§9.10) and journals for the page in one read, and at most 20 seconds after that read began; if reading takes longer, it hands out no page and answers HTTP 503 `anchor_history_read_slow`. If a recorded time of the page would lie after `server_ts` (page rule 5), it hands out no page, answers HTTP 503 `server_clock_behind` and raises an alarm. It determines the affiliation statement from what it read, as of `server_ts` (§9.10, time reference).
6. The `server_ts` of a root is the stored character string: byte-identical with the countersignature the customer holds and with the leaf in the vendor log (§9.1, §9.2).
7. Every root of a page comes from a message of the appliance the chain belongs to (§9.2). A reported root whose sender the server can no longer determine, for example from the time before edition 1.10, it lists on no page.
8. The server limits fetches of form v2 per source address and per pair of `chain_id` and source address, so that from one address ten chain-years of one chain can be fetched in one hour (about 2 300 pages); beyond that it answers this address HTTP 429 `rate_limited`. It keeps no limit that hits all senders of a `chain_id` together: otherwise anyone who knows the `chain_id`, the key holder for example, could use up the auditor's fetches. It keeps the counters in memory only (§12 item 7). Every page is a bounded read over an index; no request reads more rows than belong on one page.
9. No other output of the server changes: no flag and no number concerning affiliation in `/v1/status`, in a fleet overview or in a response; every chain receives the same form of response and the same error responses (§12).
10. The server hands out pages of form v2 only once a statements key stands in a published role list (format specification 10.7.2, §9.11), and it signs them only with a statements key; until then it answers a request for form v2 with HTTP 503 `anchor_history_v2_unavailable`.

**Fetch by the auditor (from edition 1.10).** An auditor who wants to establish the completeness of a package (format specification 8.6, 8.8, 11.2)

1. records when he requests the package (request time);
2. once the day of the request is due in the vendor log (06:00 UTC of the following day, §9.9), fetches from the vendor himself, not through the audited organisation (it can withhold material but not alter it, and its absence is then information in itself; a refusal by the vendor, HTTP 429 for example, is in contrast no information about the package, and the auditor fetches again later): all pages of form v2 of the chain and of every chain of its succession (registered chain succession, `GENESIS.predecessor_chain`, format specification 4.1), the current role list (format specification 10.7.2), the current protocol key list (format specification 7.4.7), optionally for the role check also the current list of countersigning keys (format specification 10.7.1, 10.7.4), and the extract of the vendor log for this chain (`GET /v1/log/extract`, §9.9), in addition from both places of publication the mirror extract `<YYYY>.json` of every year into which a day of the extract falls;
3. passes all of this to the verifier together with the request time, the vendor root and the roots of the time-stamping authorities he obtained himself (`--anchor-history`, `--vendor-log`, `--vendor-key-list`, `--requested-at`; format specification 10.8); he MAY pin a statements key he knows by another route (`--vendor-statement-key`); he MAY combine pages and extracts in one file `ledger-ankerhistorie/2` (format specification 8.8), and he passes the key lists with `--vendor-key-list`;
4. compares the head of the log (day and day hash) with the second publication place, another auditor or a monitoring service, and the issue times of the pages named in the report with another auditor or a monitoring service; pages of the anchor history are not at the second place;
5. keeps all inputs with the audit file; they remain verifiable offline.

**What the verifier does with it.** What the auditor did by hand up to edition 1.9, the verifier does from edition 1.10 (format specification 8.8). It checks key (statements keys only, format specification 8.8.3), signature, form and page rules of every page, uses only pages of the package's chain or of a chain linked to it whose `owner_keys` match the device of the package, and treats a page as fresh if its `server_ts` lies no earlier than 15 minutes before the request time `R`. It requires the fresh pages together to cover all tree sizes from 0 on, compares the pages with each other and with the vendor log, and takes over their roots, countersigned ones, gap witnesses and reported ones alike, as expected roots with the source "anchor history". A root that the vendor countersigned or recorded as a gap witness earlier than 15 minutes before `R` and that is missing from the package or contradicts it is `MERKLE_INCONSISTENT` (exit 2): the package then lacks entries the appliance already had before it was requested, or contradicts them. A root that is only reported then yields `ANCHOR_HISTORY_FORK` (exit 1), since the verifier cannot check its device signature. If the package lacks only a root from the 15 minutes before `R` (clocks, anchors in transit), this is a note, not a finding; the auditor then requests the package anew instead of treating it as truncated. The verifier reports every other inconsistency of the history with exit 1: `ANCHOR_HISTORY_UNVERIFIED` (key of the page not established as a statements key, or a key of another role, no page of form v2, other chain, other device, issued before the request, pages missing), `ANCHOR_HISTORY_DEFECTIVE` (signature does not hold), `ANCHOR_HISTORY_CONTRADICTION` (page violates a page rule, pages contradict each other, the vendor log or a receipt of the package) and `ANCHOR_HISTORY_FORK` (listed or omitted fork finding, recorded root beyond the handover to the successor chain, deviating root recorded no earlier than 15 minutes before `R`, root that is only reported and contradicts the package or lies beyond it before the request).

The request time is an optional input of the auditor. Without it the verifier judges no truncation and says so in the report; completeness then counts as not established, and evidence level 3 is not reached (format specification 10.9). If the auditor states a later time than the actual one, an honest package appears truncated; if he states an earlier one, the verifier checks less. Pages issued before `R` minus 15 minutes (for instance from an archive) are used by the verifier for roots, for the cross-check and for an indication "affiliated", not for coverage, completeness or the indication "not affiliated". If the entry of their key in the role list carries `widerrufen_ab`, it does not use them at all, since whoever holds the revoked key could backdate their `server_ts`; without a request time this applies to every page under such a key.

**Procedure with pages of form v1.** If a server hands out form v1 only (a server of edition 1.9 ignores the parameter `kind` and answers with v1, which the verifier recognises by `kind` and does not use), the auditor MAY continue to apply the procedure of edition 1.9: he checks the pages himself per §9.4 items 1 to 3 (JCS form, members, signature against the vendor root or a pinned key), requires their `server_ts` to lie after the request, reads all pages and passes every root whose `server_ts` lies before the request as an expected root `<tree_size>:<merkle_root>` (format specification 10.8), countersigned ones, gap witnesses and reported ones alike. If a deviation concerns only roots from the last 15 minutes before the request, he requests the package anew. On a registered chain succession or a predecessor chain in `GENESIS` he also fetches the history of the other chain; for a predecessor chain the `tree_size` handed over is its end, and a root recorded there beyond it is a contradiction. Pages of form v1 bind the chain to no device: if another appliance presented the `chain_id` of a never-anchored chain beforehand, v1 shows its roots, and this procedure reports `MERKLE_INCONSISTENT` against an honest package. If the vendor has published a role list (format specification 10.7.2, at the places of the protocol key list, §9.9), an auditor following edition 1.10 does not apply this procedure: he passes pages of form v2 to the verifier. He never passes roots from pages of form v1 as expected roots; at most he compares them himself. For a vendor without a role list the procedure applies as in edition 1.9.

The history is not a countersignature. From edition 1.10 the auditor passes its pages to the verifier (format specification 8.8); its roots are expected roots. A verifier does not evaluate pages of form v1.

### 9.8 Activation receipt

From version 1.9 every 200 answer to an activation (the first one, a verbatim repetition and a rebinding) carries an activation receipt in the member `activation_receipt`. It travels as an object per §9.4 (`statement_jcs`, `server_key_id`, `server_signature`, `statement`), from edition 1.10 with a pair under a statements key in `statement_signatures` (§9.3), with `kind` = `ledger.activation_receipt.v1` (registry `cloud_statements.activation_receipt`) and has exactly these members:

| Member | Type | Meaning |
|---|---|---|
| `kind` | const `"ledger.activation_receipt.v1"` | kind of the receipt |
| `appliance_id` | uuid | from the activation |
| `device_pubkey` | hex64 | from the activation |
| `license_commitment` | hex64 | commitment under which the vendor holds this registration at `server_ts` |
| `server_ts` | rfc3339 | time of issue by the server clock, form as in §9.4 item 2 |

It says: at `server_ts` the vendor holds the registration of `appliance_id` with this device key under this commitment. This is a statement of state, not an answer to exactly one request: an activation carries neither a time nor a nonce, and a verbatim repetition receives a receipt of the same statement. The receipt therefore proves neither possession of the license key nor that the appliance is alive; whoever holds a verification package can obtain a new one by repeating the chained activation.

It is effective when the recipient confirms §9.4 items 1 to 4: JCS form, exactly these members with these types and `kind` as above, key and signature (item 3 in the form for the recipient's edition), and `license_commitment` is that of the configured key. For accepting a rebinding, §4.1 additionally requires the appliance's own `appliance_id`, its own `device_pubkey` and freshness. A receipt is not held like a statement; the rule against older statements (§9.4) does not apply to it. It is not chained, and a verifier does not evaluate it. Reference cases: `spec/contract/activation_receipt.json`.

### 9.9 Vendor log: closing and publication

From edition 1.10 the vendor keeps a vendor log (format specification 7.4). For every UTC day from the start of the log (`erster_tag` of the protocol key list) it commits with a signed day entry `ledger.vendor_log_day.v1` to the set of all countersignatures (§9.1) and gap witnesses (§9.2) of that day, also for a day without any, has the entry witnessed by time-stamping authorities and publishes it in two places. Leaves, positions, day tree, day entry, protocol key list, extract, day leaves and their checking by the verifier are defined by the format specification in sections 7.4 and 7.5; this section governs what the vendor MUST do for this. Reported roots, refusal statements, fork findings, statements and activation receipts are not leaves. Times are whole milliseconds per format specification 2: `end(d)` is the end of the UTC day `d`, `day(ts)` the date of an instant `ts` (its characters 1 to 10, fractions cut off).

| Quantity | Value | Meaning |
|---|---|---|
| closing delay | 300 000 ms (5 minutes) | the closing of `d` does not begin before `end(d)` + 300 000 by the clock of the closing |
| lower bound for timestamps | 60 000 ms (1 minute) | a timestamp witnesses `d` only with `genTime` ≥ `end(d)` + 60 000; an earlier one shows that the day was closed too early |
| publication deadline `P` | 21 600 000 ms (6 hours) | the entry stands in both places by `end(d)` + `P`, that is 06:00 UTC of the following day; from then on `d` is due for the verifier |
| time window `W` | 172 800 000 ms (48 hours) | a timestamp witnesses `d` only with `genTime` < `end(d)` + `W` |

The time window `W` is 48 hours.

**Issuance.**

1. Every countersignature that leaves the server stands in the issuance journal before the response (§9.1).
2. Every gap witness is a leaf with the time at which the server first recorded it, in the stored character string (§9.2).
3. A day `d` comprises the countersignatures and gap witnesses with `day(server_ts)` = `d`. The time of storing does not count, since the server takes `server_ts` before storing. The closing reads the issuance journal and the recorded roots through a sequential identifier, not through a search by `server_ts`, so that no leaf stored late escapes it.
4. A day is closed as soon as its closing has begun to read its leaves. For a closed day the server issues no countersignature (§9.1) and records no gap witness: instead of the refusal (§9.5) it then answers with HTTP 503 `log_day_closed` (§9.6) and raises an alarm. A request answered this way SHOULD NOT count against the request quota.

**Closing a day.**

1. The day `d` is closed by a separate job, which also runs when the interface of the metadata server has failed. It does not begin before `end(d)` + 300 000 ms by its clock.
2. It forms for every chain with leaves on `d` the chain-day root, the position (with the `appliance_id` of the appliance to which the server bound the chain, §9.2) and the chain-day leaf (format specification 7.4.3) and hands the signing service (below, "Keys and signing service") the day `d` and these chain-day leaves as pairs of `position` and `chain_root`, optionally the expected `prev_hash`, and for a closing anew under item 3 the request for it with the premature timestamp, nothing else. The signing service fixes the `server_ts` (format specification 7.4.5), forms the fillers per the size rule (format specification 7.4.4), from these the day tree ordered by position and the day entry with the `prev_hash` of the previous day, signs it with the protocol key and returns the day entry and the day leaves (format specification 7.4.9). If the position of a filler hits another position of the day (only with a collision of SHA-256), it does not sign and raises an alarm (format specification 7.4.4). Before the job continues it checks the result: the signature under a protocol key of the effective protocol key list; the content per format specification 7.4.5 and step L2 (c) and (g), with `day` = `d`, `first_day` = `erster_tag`, `log_id` of the list and `server_ts` in the form `YYYY-MM-DDThh:mm:ss.sssZ`, at least `end(d)` + 300 000 ms and at most 60 000 ms from its clock, for an answer marked as a repetition at most 60 000 ms after its clock; every chain-day leaf it handed over among the day leaves; checks (a) to (d) of the day leaves (format specification 7.4.9); `tree_size` equal to the smallest power of two that is at least 1024 and at least the number of chain-day leaves handed over, except for a log whose list is signed by a root from the published test keys; and `prev_hash` equal to the day hash of the entry of the previous day that passed the gate (item 3) or that a person released without a timestamp under item 6, 64 zero characters for `d` = `erster_tag`. If a check fails, it requests no timestamp, never hands the entry out and raises an alarm. Then it requests timestamps per RFC 3161 over the UTF-8 bytes of `statement_jcs` (hash SHA-256) from at least two time-stamping authorities of different operators; this it MUST do. The vendor and parties affiliated with it (§9.10, §12) MUST NOT operate any of these authorities. One of the authorities MAY be one whose token identifies itself as qualified (format specification 7.5.6). Every request SHOULD carry a nonce (`nonce`) and `certReq = true`; the verifier cannot confirm a token without certificates (format specification 7.5). A day object carries at most four timestamps.
3. **Gate for the timestamps.** The vendor MAY publish a day entry only if it holds at least one timestamp that it has itself checked per format specification 7.5 against the root of the issuing authority and whose `genTime` is at least `end(d)` + 60 000 ms. An entry whose timestamps show an earlier `genTime` it MUST destroy; it never hands it out, the day counts as open again, and it closes it again later, with a new `server_ts` and the same fillers (format specification 7.4.4). So a forward jump of the clock cannot finally close a future day. The job MUST compare its clock with every `genTime` and with the `server_ts` of every newly signed result of the signing service (item 2); if they deviate by more than 60 seconds, it raises an alarm and closes no further day until the deviation is resolved.
4. Before publication the vendor MUST durably secure the entry, all timestamps, all chain-day proofs and the day leaves outside the server. A published day no longer changes; every proof is delivered from this backup, never computed anew.
5. The days are closed without gaps in their order; a missed day is caught up. A day whose entry is published the vendor never closes again: for a day there is exactly one content `statement_jcs`. It MAY sign the same content again with another protocol key, for instance after a key change; that is not a second entry. The signing service forms the new signature (below, "Keys and signing service", item 2), and it is added to the file of the day as an element of `additional_signatures` (format specification 7.4.8). The job hands the day `d` + 1 to the signing service only once it holds for `d` a timestamp checked under item 3 with `genTime` ≥ `end(d)` + 60 000 ms, or once a person has released `d` without a timestamp under item 6.
6. By `end(d)` + `P` it publishes the entry with its timestamps in both places. Timestamps that arrive later it MAY add; the entry does not change by this. If because of the gate (item 3) it cannot publish by then, it does so as soon as it holds a checked timestamp; until then the day is overdue (monitoring, below). If by `end(d)` + `W` it receives no timestamp that witnesses the day, a person in operations, never an automatic job, MAY, by way of exception from item 3, publish the entry without one, so that the sequence stays without gaps; `/v1/status` shows this. For the verifier such a day is not witnessed: receipts of this day remain uncheckable, with `VENDOR_LOG_UNVERIFIED` (exit 1).

**Tree size and fillers.** The day tree has the size given by the size rule of format specification 7.4.4: the smallest power of two that is at least 1024 and at least the number of chains with leaves on that day. The rule applies to every log from its first day; the only exception is a log whose protocol key list is signed with a root from the published test keys (format specification 7.4.4). The remaining leaves are fillers, which the vendor derives per format specification 7.4.4; a day without leaves has 1024 fillers. The published day leaves amount to 64 bytes per leaf and day, that is at least 64 KiB per day.

1. **Filler secret.** How the fillers come about is checked by no verifier (format specification 7.4.4); the vendor MAY derive them as described here. If it does not derive them, the signing service forms them from a cryptographically secure random generator, records them in its journal so that a new closing of the same day carries the same fillers, and the list names `fuellerbindung` `null`. To derive them, the vendor generates, before the first day on which it derives, a filler secret, 32 bytes from a cryptographically secure random generator, a separate one for every log; a test environment has its own. It is generated offline, in the signing procedure of the protocol key list (§9.11 item 10, transition item 1), which commits to it with `fuellerbindung` (format specification 7.4.7). Only the signing service of the log receives it (below, "Keys and signing service"), as a file provided to it alone. The signing service forms the fillers itself and hands out neither the filler secret nor a day secret nor a salt. The vendor backs up the filler secret offline in at least two locations. If it is lost, the fillers of the days formed with it can no longer be opened; this changes nothing about any proof or any check by the verifier. The filler secret applies to the whole log and is not changed. If it becomes known, the vendor states this publicly; the fillers then no longer hide the number of chains, and this changes nothing about any proof or any check by the verifier.
2. **Never public.** No published or delivered object, `/v1/status`, a statistic or an operational log included, names the filler secret, a day secret, a salt, the number of fillers or of chains of a day, or which leaves are fillers. Every proof can be formed from the secured day leaves; the filler secret is needed only for an opening.
3. **Opening.** The vendor MAY open single fillers or whole days to an auditing party (format specification 7.4.13). An opening is formed by a person in operations from the backup of the filler secret, never by the signing service on request. The opening of a whole day shows the number of chains of that day; the vendor never publishes it and never gives it to an affiliated party or to a person acting for both sides (§12 item 2 and exception (b)). It records every opening with day, scope, recipient and time, from the start of the access chain as an entry `DATA_ACCESS` with `data_class` = `chain`, `purpose` = `audit` and `access_mode` = `export` (§12, "Access chain"). If for a day it also shows the origin of the chain-day leaves, it passes on customer data; §12 applies to that.

**Restore.**

1. Published days do not change. After restoring a backup the server MUST first fetch back the published entries and the secured proofs that are newer than the backup, from the backup outside the server or from the second place, before it closes the next day. After a backup is restored, or as a new instance, the signing service signs again only once its journal reaches the published head. It takes over missing entries only from published day objects whose signature holds under a protocol key of the effective protocol key list and which link without gaps via `prev_hash` to its journal, from `erster_tag` if the journal is empty; taking over signs nothing.
2. It SHOULD mirror the leaves of days still open outside the server before it answers. If leaves are lost, it MUST state the loss publicly, at both places in the file `verluste.json`: a JSON array that is only appended to, with one object `{"von": rfc3339, "bis": rfc3339, "angegeben": rfc3339, "grund": string}` per loss. `von` and `bis` bound the `server_ts` whose leaves may be missing; the statement names no number of leaves and no chain. The verifier does not read the file. The file stands at both places from `erster_tag` on, as `[]` without a loss. `von` and `bis` have the form `YYYY-MM-DDThh:mm:ss.sssZ` and include both bounds; `grund` names no customers, no chains and no persons. The verifier reports receipts whose leaf is missing as `RECEIPT_NOT_LOGGED` (exit 1), never as a forgery; the chain stays valid.
3. The issuance journal, the data of the log, the device-key journal (§9.7), the binding journal, the declarations, the affiliation register (§9.10) and the journal of the signing service (keys and signing service, item 2) belong to the data the vendor backs up; the filler secret it backs up offline ("Tree size and fillers", item 1).

**Keys and signing service.**

1. The vendor signs the protocol key list `ledger-protokollschluessel/1` (format specification 7.4) offline with the vendor root; no running service holds or needs its private part; the metadata server takes its public key from its configuration (§9.11 item 6). The vendor root signs only objects whose member `format` names their purpose: the list of countersigning keys (format specification 10.7.1), the role list (format specification 10.7.2) and the protocol key list, in the signing procedure per §9.11 item 10. The protocol key list names `log_id`, `erster_tag`, the filler commitment, the publication places and the protocol keys; every new version keeps every key ever named, and `log_id`, `erster_tag` and `fuellerbindung` never change. It SHOULD name a standby key whose private part stays offline; if the active key is compromised, the vendor switches to the standby key and publishes a new version with `widerrufen_ab` for the old one, without a new key appearing.
2. The active protocol key is generated by the signing service; only its public part leaves it. A protocol key signs only day entries the signing service has formed itself; no key of another role signs a day entry, and no key stands in two roles (otherwise the protocol key list is ineffective for the verifier, format specification 7.4.10, 10.7.4). The `key_id` and public key of every key MUST be unique across all versions of all three lists (§9.11 item 1); the verifier compares the roles by the public key (format specification 7.4.10, step L1, and 10.7.4), but an auditor reads an identifier in one meaning only. The signing service is a separate service: it keeps its private key in a file accessible to it alone, never in an environment variable that other services also receive; a reserve generated offline is likewise provided to it only as such a file. It offers no interface that signs arbitrary bytes or a finished entry, holds no access token of the fleet and receives only the chain-day leaves of the day to be closed (closing a day, item 2), never leaves of a chain (format specification 7.4.2), no `chain_id` and no `appliance_id`. It does not start if its public key equals a key of another role or stands under another role in any version of one of the three lists (§9.11), of the operation as of a test environment. It receives the filler secret only as a file provided to it alone. It keeps its own journal of the entries it has signed, which is only appended to. For a day `d` it signs only if `d` = `erster_tag` and the journal is empty, or if `d` follows the latest day of the journal; it does not sign before `end(d)` + 300 000 ms by its clock. A request for a day its journal already holds it answers with the entry last recorded there and its day leaves, marked as a repetition, without signing again. It closes the latest day of the journal anew (closing a day, item 3) only if the request asks for this explicitly and encloses a timestamp over the previous entry of this day that it confirms per format specification 7.5 against a root of a time-stamping authority of the log and whose `genTime` lies before `end(d)` + 60 000 ms. `prev_hash` is 64 zero characters for `d` = `erster_tag`, otherwise the day hash of the entry its journal last records for the previous day; if an expected `prev_hash` sent along differs from it, it does not sign. It MAY sign the entry its journal last records for a day unchanged with a further protocol key it holds (closing a day, item 5): for this it accepts only the day, reads this entry from the journal, signs exactly its `statement_jcs` and returns the signature as an element of `additional_signatures` with `alg` = `ed25519` (format specification 7.4.8); this is no closing anew.
3. A test environment keeps its own log with its own `log_id`, which begins with `staging-`, its own protocol key, its own filler secret and its own list, which is not signed with the vendor root of the production operation.

**Publication.** The vendor publishes in two places, both in the same file form (below), each under the base address that the protocol key list names in the member `orte` (format specification 7.4.7): place 1 within the vendor's operation, for instance in its download area, place 2 outside it; for a log under trial both MAY lie within the vendor's operation (below). An address is `<place>/<path of the file>`. In addition the metadata server serves read-only, without login, under `/v1/`; these routes are not a place in the sense of `orte`:

| Route | Response |
|---|---|
| `GET /v1/log/keys` | the current protocol key list |
| `GET /v1/keys/roles` | the current role list (§9.11) |
| `GET /v1/keys/countersigning` | the current list of countersigning keys (§9.11) |
| `GET /v1/log/head` | the latest published day as `{"entry": …, "timestamps": […], "additional_signatures": […]}` |
| `GET /v1/log/day/<YYYY-MM-DD>` | this day in the same form |
| `GET /v1/log/leaves/<YYYY-MM-DD>` | the day leaves `ledger-tagesblaetter/1` of this day |
| `GET /v1/log/extract?chain_id=<uuid>[&from=<YYYY-MM-DD>][&to=<YYYY-MM-DD>]` | an extract `ledger-protokollauszug/1` for this chain over at most 31 days |
| `GET /v1/access-chain` | the access chain statement (§12, "Access chain", item 9) |
| `GET /v1/access-chain/day/<YYYY-MM-DD>` | the day head of the access chain for this day |

`entry` is the day entry as `{statement_jcs, server_key_id, server_signature}`, `timestamps` are its timestamps (0 to 4, format specification 7.4), `additional_signatures` further signatures (0 to 3, format specification 7.4.8). An extract covers every day of its range: the day object with all timestamps and, for every day, a proof, present or absent. Without `from` the range begins on the day on which the chain first has a leaf, without `to` it ends at the head, after at most 31 days. The server forms the extract from the secured data of the published days, never anew; it answers an unknown chain with HTTP 404 `unknown_chain` as in §9.7.

**File form.** Both places carry the same files under the same paths. Place 2 accepts additions only (below, "What a reader can assume at place 2") and is fed by a separate job with separate access, which the operation of the metadata server does not hold. Timestamps and additional signatures (format specification 7.4.8) that arrive later are added to the file of the day as an addition; `entry` never changes:

| File | Content |
|---|---|
| `keys.json` | the protocol key list |
| `rollenliste.json` | the current role list (§9.11) |
| `rollenliste/<version>.json` | every version of the role list |
| `schluesselliste.json` | the current list of countersigning keys (§9.11) |
| `schluesselliste/<version>.json` | every version of this list |
| `days/<YYYY>/<YYYY-MM-DD>.json` | the day object `{"entry": …, "timestamps": […], "additional_signatures": […]}` |
| `leaves/<YYYY>/<YYYY-MM-DD>.json` | the day leaves of this day |
| `<YYYY>.json` | mirror extract of the year: an extract with `chain_id` = `null` and empty `chain_days` that carries all day objects of the year |
| `head.json` | the latest published day |
| `verluste.json` | the statements of lost leaves (below, "Restore", item 2) |
| `zugriffskette.json` | the access chain statement (§12, "Access chain", item 9) |
| `zugriffskette/<YYYY>/<YYYY-MM-DD>.json` | the day head of the access chain for this day |

**What a reader can assume at place 2.** Place 2 is, for instance, a branch of a public repository at a hosting provider. The vendor sets it up as follows:

1. The history of the place is protected against overwriting and deletion; every change is an addition that a reader recognises as such.
2. The access with which the job feeds place 2 can only add and cannot change the protection. Nor can it trigger a job at the provider that may do more than the access itself, for instance an integration workflow with write permissions of its own.
3. A monitor compares every state of place 2 with the previous one and alerts the vendor on every change that is not an addition and on every deletion.
4. A timestamp or an additional signature that arrives later, and every new statement in `verluste.json`, is added as an addition, never by rewriting the history.

Every reader MAY keep copies of their own and compare against them. Whoever holds the account at the provider can lift the protection; a reader notices this only by comparison with an earlier copy of their own or of another observer (no evidence produced by LEDGER).

The protocol key list names both places in the member `orte`, one within the vendor's operation and one outside it, except for a log under trial (`log_id` begins with `staging-`, keys and signing service, item 3), whose places MAY both lie within the vendor's operation (format specification 7.4.7); the places can change only with a new version signed with the vendor root. Day entries and day leaves stand in both places, as do the current role list, the current list of countersigning keys (§9.11) and the statement and day heads of the access chain (§12). With the day leaves anyone can check that the positions of a day are strictly ascending, that their number equals `tree_size` and that their tree yields the root of the entry (format specification 7.4); so different versions of a chain under the same day root become apparent. The vendor does not record fetches under `/v1/log/` (§12 item 7).

**Monitoring.**

1. `/v1/status` shows the last closed, signed, witnessed and published day and every overdue day, without the number of chains or of fillers of a day.
2. If a day does not stand in both places by `end(d)` + `P`, the status shows red and the vendor is alerted (missing-day alarm).
3. A monitor outside the metadata server checks at least every 24 hours that the log progresses, and otherwise alerts the vendor.
4. At the second place the check of the day leaves (order, number, root, size rule) SHOULD run daily. An installation of the vendor's own that anchors like any customer installation SHOULD check the day entry of its chain daily: signature, timestamps, inclusion of its countersignatures, and day leaves.

**What a violation yields at the verifier.** If the auditor passes the log (§9.7), the verifier shows violations by the vendor as follows (format specification 7.4):

| Violation by the vendor | Finding | Exit |
|---|---|---|
| day entry of a due day missing or not passed | `VENDOR_LOG_UNVERIFIED`; receipts of this day without day entry | 1 |
| day entry without a timestamp that witnesses the day | `VENDOR_LOG_UNVERIFIED`; receipts of this day not checkable | 1 |
| confirmed timestamp with `genTime` before `end(d)` + 60 000 ms (day closed too early) | `VENDOR_LOG_CONTRADICTION` | 1 |
| two different entries for one day; an entry that does not follow on from the previous day or skips days; a signed entry that violates a format rule | `VENDOR_LOG_CONTRADICTION` | 1 |
| signature or timestamp does not hold; a proof does not match the day root | `VENDOR_LOG_DEFECTIVE` | 1 |
| an issued countersignature is missing from the witnessed day (omission, loss, missing entry in the issuance journal) | `RECEIPT_NOT_LOGGED` | 1 |
| a recorded root contradicts the package | `LOGGED_ROOT_MISMATCH` | 1 |
| log and anchor history name different roots of a chain | `ANCHOR_HISTORY_CONTRADICTION` | 1 |

Each of these findings can also occur with an honest chain; therefore none of them makes a chain invalid. The verifier does not report a violation of the size rule or of the derivation of the fillers: that the size is a power of two and at least 1024 is shown by the day leaves (format specification 7.4.9); whether it is the smallest permitted one is shown only by the opening of the whole day together with proof of origin for every other leaf, and the derivation from the filler secret only by the filler secret itself, checked against the filler commitment (format specification 7.4.13).

### 9.10 Affiliation with the vendor

From edition 1.10 the vendor states for every chain whether a customer of the chain is affiliated with it. The countersignature binds a chain to a party outside the control of its key holder (format specification 7); for the time of an affiliation it does not establish a party independent of the customer. The indication is a signed assertion of the vendor in the anchor history (§9.7), signed with a statements key (§9.11). The verifier displays it and checks its signature, its form, its binding to chain and device and its cross-check with other pages passed, not its correctness (format specification 8.8); it changes neither an exit code nor a finding.

**Vendor** in this section is every party that holds a countersigning key (§9.1), a statements key, a manifest key (§9.11), a protocol key (§9.9) or the vendor root (format specification 10.7) or decides on their use, and every party that operates the metadata server.

**Customer of a chain** at a point in time is (1) the licensee under whose license the appliance the chain belongs to is registered at that time, and (2) the operator declared for this license, that is the party for which the appliance records. A chain belongs to the appliance to which the server bound it (§9.2 step 1) or, if the server knows the chain only through a registered chain succession, to the appliance of that succession.

A chain is **affiliated with the vendor** at a point in time if at that time at least one of these relations exists between one of its customers and the vendor (code in parentheses):

1. The customer is the vendor itself, for instance with its own installations for operation, testing or demonstration (`vendor`).
2. The customer controls the vendor directly or indirectly (`controls_vendor`).
3. The vendor controls the customer directly or indirectly (`controlled_by_vendor`).
4. Both are controlled directly or indirectly by the same natural or legal person or by several persons acting together (`common_control`).
5. Either of the two sides, whichever it is, holds directly or indirectly at least 20 percent of the voting rights or of the capital of the other, without controlling it (`participation`).
6. A natural person belongs at the same time to the management or the supervisory body of both (`shared_management`).
7. The customer is a person in a key management position of the vendor or of a party that controls it (a member of the management or of the supervisory body, or another person with the authority and responsibility for planning, directing and controlling its activities), a close member of the family of such a person (spouse or domestic partner, children, children of the spouse or domestic partner, and dependants of the person or of the spouse or domestic partner) or a party controlled by one of these persons (`key_management`).
8. One of the relations 1 to 7 ended less than 24 months before the time in question (`former_relation`).

**Control** means: holding the majority of the voting rights, being able to appoint or remove the majority of the members of the management or supervisory body, or exercising a controlling influence on the basis of a contract, of the articles of association or in fact. The indication follows these criteria, not the product edition and not data in the verification package (`GENESIS.customer_id`, `GENESIS.edition`). The relations are modelled on the related entities and persons of IAS 24.9, including persons in key management positions and their close family members (relation 7), and on the grounds excluding a statutory auditor under § 271(2) of the Austrian Commercial Code (UGB), whose after-effect of 24 months relation 8 adopts; relation 6 goes beyond IAS 24.11(a). It is not a legal classification. The neutrality rules are modelled on the independence rules for statutory auditors (§ 271 UGB, IESBA Code), with one openly stated deviation: a body with the same owner as the vendor may be a customer; the anchor history states it as affiliated, and its chains reach the evidence levels under the same rules as any other.

**24 months** after a time T is the same day at the same time of day (UTC) two calendar years later; if T falls on 29 February, it is 1 March two years later, 00:00:00.000Z.

The vendor MUST keep the affiliation for every customer by the same criteria and output it in every page of the anchor history `ledger.anchor_history.v2` as the member `affiliation` (§9.7). For an affiliated customer all rules of this specification apply unchanged: the same keys, endpoints, quotas, retention periods and the same vendor log (§12).

**Bases.** In every member `bases` the codes stand strictly ascending in this order (order of character codes):

| Code | Meaning |
|---|---|
| `common_control` | vendor and customer are controlled by the same side |
| `controlled_by_vendor` | the vendor controls the customer |
| `controls_vendor` | the customer controls the vendor |
| `former_relation` | one of the other relations ended less than 24 months before the time in question |
| `key_management` | the customer is a person in a key management position of the vendor or of a party controlling it, a close family member, or a party controlled by them |
| `participation` | participation of at least 20 percent without control |
| `shared_management` | the same person in the management or supervisory body of both |
| `vendor` | the customer is the vendor itself |

**Time reference.** For every page the server determines the indication as of the `server_ts` of the page:

1. **Customers over time.** From edition 1.10 the server MUST record every period in which an appliance is registered under a license, with the licensee and the declared operator of this license (binding journal). It appends to it in the same step as the activation, the takeover of a license on renewal, the replacement of a license together with the registrations removed in it, a transfer by the administration and the declaration of an operator, and it never changes an entry. A replacement of the license key (§4.1) and a rebinding keep the license and change nothing; a takeover on renewal changes the licensee from the time it takes effect. If another licensee takes over the license, the declaration of the operator ends with it; if the same licensee takes it over or it is renewed without a takeover, the declaration remains. A declaration that changes nothing about the declared operator appends nothing to the binding journal, even if it names other relations than the previous one; whether it holds back `known_since` is stated in item 2 and obligation 2 below. Every row of the binding journal takes effect at the earliest one minute after it is entered (item 5); a row that no page already issued can contradict, for instance the first activation of an appliance, MAY take effect when it is entered.
2. **`known_since`** is the earliest time from which the binding journal determines every customer of the appliance the chain belongs to without gaps up to the `server_ts` of the page; `null` if it cannot determine them at this `server_ts`. For the time before `known_since` the page says nothing negative; it MAY list periods before it. At the changeover to edition 1.10 the following applies for an appliance registered at that time: the licensee is known from the latest recorded event that can have changed it (issue, renewal, transfer by the administration); the operator is known only from its declaration under the license terms per this edition, unless the vendor knows it otherwise. If neither can be determined, `known_since` is the time of the changeover or later. As long as the affiliation register is not maintained (obligation 4 below), `known_since` is `null`, even if the binding journal determines the customers. Likewise the binding journal does not determine the customers for the time in which the appliance is registered under the license of a declaration (obligation 2 below) from the effective time of that declaration, as long as the declaration is open at `server_ts`, whatever it names; if this time lasts at `server_ts`, `known_since` is `null`. So the page of a chain whose appliance is or was registered under the license of a declaration open at `server_ts`, from that declaration's effective time, says "not affiliated" for no time up to the end of that registration. The declaration holds back no other chain, neither a chain under another license of a party it names nor one whose appliance was registered under its license only before its effective time: there a relation from the declaration appears only once it is entered per obligation 3, an earlier page may have said "not affiliated" for that time, and `recorded_ts` shows the delay (item 5). After a takeover by another licensee the operator is not determined until its declaration: until then `known_since` is `null`, afterwards it does not lie before the time this declaration takes effect.
3. **Periods.** The affiliation register (below) names periods with bases per license and per customer. From them the server forms the time course of the customers of the chain (at every point in time the union of the bases of all its customers), clips it to the time from the activation of the appliance the chain belongs to up to `server_ts`, and outputs the largest possible periods with constant, non-empty bases, ordered by `from`. The `recorded_ts` of a period is the latest `recorded_ts` of the register entries that contribute to it: the entries that hold within it, and the entry that ends it, also when it ends it by starting a basis the period does not have. An entry ends a period by its start only where its own `from` lies; if it applies to the chain only later, because its customer becomes a customer of the chain or the appliance becomes registered under its license only then, the binding journal ends the period, not a register entry. A period still lasting at `server_ts` has `until = null`; `merged` is `false`. An entered end that does not yet take effect at `server_ts` does not change the page: the period is open there, and the end contributes to `recorded_ts` only from the time it takes effect. If a basis of the relations 1 to 7 ends for a subject of the register (a license or a customer, obligation 1) at a time T, that is it stands in a register period of this subject immediately before T and in none at T, the period from T to 24 months after T with the basis `former_relation` belongs to this subject; it enters the time course like every entry of this subject, that is for a customer only while it is a customer of the chain, for a license only while the appliance is registered under it. Whether a basis ends is determined only by the register periods of the same subject: if the appliance changes license or a customer stops being a customer of the chain, no basis ends; if a basis ends in the entries per customer while an entry per license continues it, `former_relation` stands next to it, which overstates and never shortens. A register entry carries `former_relation` only for a relation that ended before it was entered, with `from` equal to the end of the relation and `until` 24 months after this end, both of which MAY lie before the entry (item 5); from such an entry the server derives no further period. If a derived period `former_relation` holds within a period of the page or ends it, the register periods of its subject that end with the ended basis at T contribute for it, together with the entries that end them at T; it thus contributes the latest `recorded_ts` of these entries.
4. **More than 16 periods.** Then the server merges the two periods with the earliest `from` into one (`from` of the earlier, `until` of the later, `bases` united, the later `recorded_ts`, `merged = true`). If the new period then adjoins the following one and both have the same `bases`, it merges these two as well in the same way, so that page rule 10 (§9.7) holds. It repeats both until at most 16 periods remain and no two adjoining ones have the same `bases`. Merging only widens; it removes no point in time at which the chain is affiliated. The server therefore MUST NOT refuse a page and MUST NOT leave out a period.
5. **Immutability.** A period whose end is entered by a later entry never ends before the time of that entry, and at the earliest one minute after it: an end never acts retroactively. A period entered with start and end at once, an entry with `former_relation` (item 3) included, by contrast ends at its entered end, even if that lies before the entry: no earlier page can have shown it, it only adds, and `recorded_ts` shows the delay (obligation 3 below). The server takes the entry time of a register entry, of a row of the binding journal and of a declaration (obligation 2 below) when writing begins, and at most 20 seconds later the entry is visible to every read. Together with the limit on the read for a page (§9.7, obligation 5), every page thus shows every end, every row and every declaration that takes effect up to its `server_ts`, and no honest page narrows the statement of an earlier one. A period is never deleted or shortened; a correction only adds or widens. If two pages contradict each other about a point in time, the vendor has violated this rule; a verifier that has both reports `ANCHOR_HISTORY_CONTRADICTION` (exit 1, format specification 8.8).
6. **Chain succession.** Both chains of a registered chain succession belong to the same appliance; their pages show the same time course, and every package is judged over its own period (format specification 8.8).

**Duties for the register.**

1. **Register.** The vendor keeps an affiliation register that is only appended to: entries per license (through an identifier of the license that survives the replacement of the license key and a takeover) or per customer (`customer_id`), not per pair, each with bases, start `from`, optional end `until`, entry time `recorded_ts`, an identifier of the person who made the entry (no name) and the reason. An entry per customer applies to a chain while this customer is licensee or declared operator of the license under which its appliance is registered; an entry per license, while the appliance is registered under this license. The reason is a category with a case number that points to records of the vendor outside the metadata server, no free text. A period ends through a new entry with its own entry time. The register contains no company names and no names of persons, not even in the reason.
2. **Declaration.** The license terms MUST oblige the licensee to declare at purchase and at every renewal whether it has recording done for another party (operator) and whether licensee or operator are affiliated with the vendor in the sense of this section, and to report every change without delay. Independently of a declaration the vendor MUST enter every case it knows from its own records. The vendor records every declaration that reaches the server with its entry time and only appends to this record; a declaration writes nothing into the register. Its **effective time** is one minute after its entry (time reference items 1 and 5). Among the declarations of one licensee for a license, the one made last governs the operator; one made earlier that arrives later does not change it. A declaration **changes something** if it is the first for its license or the first after a takeover by another licensee, if it was made earlier than the governing one, or if it names another operator or other relations than that one. Such a declaration is **open** until a person whose latest recorded query showed it (§12 item 6) records, with the person's identifier, the time and a reason per obligation 1, that the person has processed the declarations of that query. Before that, the person enters per obligation 3 every relation that one of these declarations names and that the register does not already name for the time the declaration speaks for. A recorded reconciliation (obligation 4) likewise processes the declarations that the latest recorded query of its person showed. These rules apply to every declaration alike, whatever it names, and the record of the processing names no content of a declaration. The vendor processes every declaration without delay. It SHOULD hold query and processing at a fixed rhythm, for instance once on every working day, also when no declaration is open: so the number and time of the entries for query and processing in the access chain (§12, access chain, items 1 and 9) do not depend on when and how many declarations arrive; every entry per obligation 3 writes an additional entry there (§12, access chain, item 1).
3. **Time of entry.** A change MUST be entered with the time it takes effect, at the latest on the day on which it takes effect; if the vendor learns of it later, it enters it without delay with the time it took effect. A period MAY therefore begin before its entry; `recorded_ts` shows the delay. If the vendor learns of a relation of a party from a declaration and its records do not show when the relation began to take effect, its start is the time at which the latest earlier declaration was made that names this party as licensee or as operator, for whichever license, and does not name this relation for it; if there is none, the earliest time from which the party holds a license or the licensee of a license for which a declaration names the party as operator holds that license. So the statement reaches back as far as no declaration excludes the relation, equally far for every license of the party. If a declaration names `former_relation` and the records do not show when the relation ended, the vendor takes as the end the time at which the declaration was made, and in addition earlier ends at intervals of at most 24 months back to this start, so that the entries `former_relation` (time reference item 3) cover the whole time from this start. If a declaration names an operator that the declaration made last before it by the same licensee for this license did not name, an entry per customer applies to that operator only from its effective time (obligation 1); for the time before, the vendor enters the operator's relations per license, from the time at which that earlier declaration was made, without one from the time from which the licensee holds the license, in either case not before the start of the relation, and with the effective time as the end. From this end the server derives `former_relation` for the license (time reference item 3); this overstates and never shortens.
4. **Reconciliation.** At least every three months the vendor MUST reconcile the register with its own records and the declarations and record the reconciliation. The register counts as maintained from the first recorded reconciliation and stays so, even if a reconciliation is overdue; the server reports an overdue reconciliation to operations.
5. **Same criteria.** There is one register for all customers, including the vendor's own installations (basis `vendor`) and its monitoring and demonstration installations.

**Public disclosure of the affiliated companies.** The vendor MUST state publicly and unsigned the companies that stand, or in the last 24 months stood, in one of the relations 2 to 6 with it, for instance together with its legally required company information on its website: company, register number, basis, start and, where applicable, end. The download area and other places MAY refer to this disclosure instead of repeating it; so the metadata server holds no company names. The disclosure names no customer relationship and no administrative event and is not a verifier input. It allows an auditor who knows whom they are auditing to measure a persistently false indication "not affiliated" against public facts. For relation 7 it names no person and no company, only that the vendor applies this relation.

What the indication does not achieve is stated in section 11.2 of the format specification.

### 9.11 Key roles of the vendor

From edition 1.10 the vendor signs in running operation with keys of separate roles; every key has exactly one role, for its whole lifetime (format specification 10.7.3). Up to edition 1.9 a countersigning key signed all signed objects of the vendor. The vendor root is kept offline and signs only the three lists that name the keys of the roles.

| Role | Key | signs | named in |
|---|---|---|---|
| `countersigning` | countersigning key | countersignatures (§9.1); during dual operation (below) also the envelope (§9.4) of license statements, refusal statements and activation receipts, and pages of form v1 (§9.7) | list of countersigning keys `rekorder-herstellerschluessel/1` (format specification 10.7.1) and role list |
| `statements` | statements key | license statements (§9.4), refusal statements (§9.5), activation receipts (§9.8) and pages of the anchor history (§9.7) | role list `ledger-schluesselrollen/1` (format specification 10.7.2) |
| `update_manifest` | manifest key | only the envelope of the update manifest (§9.4) | role list |
| `protocol` | protocol key | only day entries of the vendor log (§9.9) | protocol key list `ledger-protokollschluessel/1` (format specification 7.4.7) |

The update key against which the updater checks update bundles (§1) belongs to none of these roles; nothing changes for it.

1. **One role per key.** A key signs only objects of its role. The `key_id` and public key of every key are unique across all versions of all three lists, and no key stands under two roles. No list names the public key of the vendor root.
2. **Projection.** The list of countersigning keys names exactly the entries of role `countersigning` from the role list of the same signing procedure, with `key_id`, `pubkey`, `gueltig_ab`, `gueltig_bis` and `widerrufen_ab` equal character for character. It keeps its format and place, so that recipients and verifiers of edition 1.9 continue to read it (format specification 10.7.1). The role list never stands in a verification package and never in the place of this list.
3. **Signing paths.** The countersignature path signs only objects with exactly the four members of §9.1. In dual operation a countersigning key additionally signs the envelope over the `statement_jcs` of license statements, refusal statements and activation receipts and pages of form v1 that the statements service hands over. Before the service holding the countersigning key signs such a `statement_jcs`, it MUST read it itself: it consists of printable ASCII (format specification 2), is I-JSON without duplicate member names and equal to its own JCS form, and its member `kind` is exactly one of the strings `ledger.license_statement.v1`, `ledger.anchor_refusal.v1`, `ledger.activation_receipt.v1` and `ledger.anchor_history.v1`. An object without `kind`, and thus every signed object of a countersignature, it never signs on this path. It records every signature it makes this way with the SHA-256 of the bytes, the kind and the time; it SHOULD sign only if the signature of a statements key valid at that time holds over the same bytes. The statements path signs only kinds of role `statements` and never an object without `kind`. The manifest key signs only the envelope of the update manifest, a protocol key only day entries (§9.9).
4. **Custody.** Every private key that a running service uses lies with exactly one service, and no service holds keys of two roles; the vendor MUST keep to this. Reserves, the manifest key and the vendor root lie offline, with no running service.
   - The statements key is held by the statements service, a separate service, not the one that holds a countersigning key. The active statements key is generated by the statements service; only its public part leaves it. It keeps its private key in a file accessible to it alone, never in an environment variable that other services also receive; a reserve generated offline is likewise provided to it only as such a file.
   - The statements service forms every statement itself from stored records: license statements from the record of the license, refusal statements from the recorded gap witness, activation receipts from the registration and pages of the anchor history from roots, fork findings, journals and affiliation register; it is the part of the server that issues pages per §12 item 6. It signs only what it has formed itself and offers no interface that signs arbitrary bytes. It does not start if its public key equals a key of another role or stands in a list under another role.
   - No running service holds the manifest key. The vendor signs the envelope of the update manifest at release; the server delivers the stored signature (§9.4).
5. **Pages.** The server hands out pages of form v2 only once a statements key stands in a published role list, and it signs them only with a statements key (§9.7 duty 10). Pages of form v1 stay byte for byte under a countersigning key until the end of dual operation and afterwards carry the signature of a statements key.
6. **Publication.** The current role list and the current list of countersigning keys stand with every version in both places of the protocol key list (§9.9, "File form"). Both lists are also enclosed with every installation and every update bundle, a security fix included. They are public (§12, "What is public"). The metadata server hands out one of the three lists (§9.9, "Publication") and bases a decision on it only if it is effective (format specification 10.7.1, 10.7.2, 7.4.7), that is, every rule of its format holds and its signature holds against the vendor root. It takes the public key of the root from its configuration, the same for all three lists, never from a list, a file next to it or a response. As for the verifier (format specification 7.4.7, 10.7.1, 10.7.2: the version with the greatest `version` is effective), a version is moreover effective for the server only if its `version` is greater than that of every version of the same format it has ever read as effective and it carries forward each of these versions by the rules of its format, or if it is byte-identical to the highest such version. It keeps the highest effective version durably, across every restart; a smaller `version`, or the same `version` with other bytes, never takes it back to an earlier version. A list that is not effective it treats like one it cannot read: it does not hand it out, raises an alarm and keeps going by the last effective version of the same format; if it has none, it issues no signature that it would have to judge by that list. It issues a signature under a countersigning or statements key only if the key is valid at the `server_ts` of the signed object by these lists and has the role under which it signs (format specification 10.7.1, 10.7.2); otherwise it issues nothing and answers with HTTP 503 `signing_unavailable` (§9.6), a heartbeat with 200 without `license` (§9.3), and for an anchor it records nothing; the anchor stays due. The vendor MUST keep to both.
7. **Role list at a recipient of edition 1.10.** An appliance of edition 1.10 keeps the role list as a file next to the list of countersigning keys and reads it like that list. It takes over a new role list only if it holds against the pinned vendor root, has a higher version or is byte-identical, and matches the list of countersigning keys in use; otherwise it keeps the previous one and warns. It receives the role list with the installation and with every update bundle; for this it needs no effective statement, since security fixes do not depend on one (§9.3). It does not accept a countersignature under a key to which the role list gives another role. The portal never hands out a list of countersigning keys that names a public key to which the role list gives another role.
8. **Reserve, change and compromise.** Every role list names besides the active statements key a reserve key of role `statements` whose private part is kept offline; the vendor MUST keep to this. A change of the statements key needs only a new version of the role list in which the reserve becomes active; it does not affect recipients of edition 1.9. A change of the countersigning key changes the list of countersigning keys and the role list in the same procedure and is distributed before the change; the procedure SHOULD name in both lists a reserve key of role `countersigning` whose private part is kept offline. If a key is compromised, the vendor switches to the reserve of its role and publishes a new version with `widerrufen_ab` for the old one.
9. **Test environments** have a root, a role list and keys of their own.
10. **Signing procedure.** The vendor root signs the three lists offline on a machine without network, from public keys, validity data and the most recently published version of every list. Before signing, the procedure checks: every key ever named is still named; every key has one role across all versions of all lists; no entry names the root; the projection (item 2) holds; `ende_doppelbetrieb`, once set, is unchanged and lies at least 180 days after `ausgestellt` of the version that first carries it; `log_id` and `erster_tag` are unchanged, `fuellerbindung` is unchanged once set; no place in `orte` of the protocol key list ends with `/` or contains `?` or `#` (format specification 7.4.7). The procedure records the SHA-256 of the signed bytes, and a second machine checks every list against the root before publication.

**Transition from operation with one key (format specification 10.7.5).**

1. **Preparation.** Before the first operation of a server of edition 1.10 and before `erster_tag`, a signing procedure collects the public parts of the keys: the active statements key is generated in the statements service, the active protocol key in the signing service (§9.9, item 4 above); the reserves of both roles, the manifest key, the filler secret (§9.9) and optionally a reserve of role `countersigning` are generated offline. It signs the role list in version 1, the protocol key list in version 1 and, with a reserve of role `countersigning`, a new version of the list of countersigning keys.
2. **Dual operation.** From the first operation of a server of edition 1.10 the previous countersigning key signs countersignatures, pages of form v1 and the envelope of the three statements to the appliance. A statements key signs pages of form v2 and the same three statements a second time in the member `statement_signatures` (§9.3). The manifest key signs the update manifest, a protocol key the day entries.
3. **End of dual operation.** From the time `ende_doppelbetrieb` of the role list a statements key signs the envelope and the pages of form v1, and countersigning keys sign only countersignatures. The vendor sets this time in a new version of the role list at least 180 days in advance and only if it no longer supports any appliance that checks statements only against the list of countersigning keys. A software version that checks statements by roles MUST therefore be installable for every supported appliance as long as its statements are still effective: afterwards an appliance of edition 1.9 accepts no feature updates (below, "What recipients of edition 1.9 continue to accept"). Once set, `ende_doppelbetrieb` stays unchanged in every later version.

**What recipients of edition 1.9 continue to accept.** Until the end of dual operation they accept countersignatures under countersigning keys of their list and license statements, refusal statements and activation receipts in the envelope under a countersigning key; they ignore `statement_signatures`, and their list never names a key of another role. Afterwards statements are no longer effective for them: they show the last effective statement as stale (§9.4), a rebinding after a key replacement does not count as accepted (§4.1), and a 403 to an anchor is an ordinary failure (§9.5). They no longer accept feature updates, which need an effective statement with `updates` (§9.4); security fixes are unaffected (§9.3). Recording, chain and countersignatures continue (§9).

What the separation of roles does not achieve is stated in section 11.2 of the format specification. No verification package shows how the vendor keeps its keys in custody (no evidence produced by LEDGER).

## 10. Silence alarm: expectation table

If the hourly heartbeat of an activated appliance stops, the cloud alarms according to a fixed table. The reference is the time since the last valid (signature-verified) heartbeat for this `appliance_id`:

| Silence duration | Mail behaviour | Recipients |
|---|---|---|
| < 3 h | **exactly 0** mails | - |
| ≥ 3 h | **exactly 1** silence mail (no repetition) | [customer contact from the license record, vendor] |
| ≥ 24 h | **exactly 1** additional escalation mail (no repetition) | [customer contact from the license record, vendor escalation list] |

At most two mails are therefore sent per silence episode. A valid heartbeat arriving again ends the episode; a later new silence starts a new episode. The test expectation (Mailhog assert) checks exactly against this table.

### 10.1 Subject patterns

Subject lines are fixed, language-neutral and machine-checkable; the mail body is German until an English website exists (decision of 02.10.2026, from edition 1.10); only then does it follow the license language (`language`).

| Stage | Subject (exact) |
|---|---|
| 3 h | `[LEDGER] HEARTBEAT-STILLE 3H <appliance_id>` |
| 24 h | `[LEDGER] HEARTBEAT-STILLE 24H-ESKALATION <appliance_id>` |

Check regex: `^\[LEDGER\] HEARTBEAT-STILLE (3H|24H-ESKALATION) [0-9a-f-]{36}$`

## 11. Alarm contact address: origin and display

The recipient address for silence mails comes from the **license record** at the vendor (created at purchase, updatable by the customer). It is **personal data**. Which data the metadata server holds beyond it, who may see them and how the vendor separates them from affiliated parties is governed from edition 1.10 by §12; no customer login exists in the cloud. The appliance portal displays this address as the "alarm address held by the cloud", so the customer can always see where alarms would go in a silence case. In air-gap / egress-off mode the cloud silence alarm is not active; the portal states this explicitly.

## 12. Data held by the vendor and information barrier

**What the vendor holds (from edition 1.10).** Besides the alarm address (§11) the metadata server stores:

- on licenses: check value of the license key (§4.1) and commitment, replaced commitments, the customer identifier `customer_id`, edition, term, order and revocation data and the administrative events on the license;
- on registrations: `appliance_id`, license, device key together with the device-key journal (§9.7), software version, language, time zone and time of activation, but not the identifier `device_key_id` (§4);
- the heartbeats with their full content (§5): counters per event type, provider class and alarm rule, gaps, storage and mode; a customer's scope of use and provider mix can be read from them;
- on chains: the binding to the appliance, every recorded and reported root with time and signature, chain successions, fork findings and the state of the alarms;
- the issuance journal (§9.1), the binding journal, the declarations of the licensees and the affiliation register (§9.10) and the data of the vendor log including the filler secret (format specification 7.4, §9.9);
- operational logs, the state of the rate limiting and backups of all of this.

In this section these data and the data in the vendor's order system (company, contact, payment) are called customer data. Contents of the recording never reach the vendor (§2). In addition, from its start, the vendor holds the access chain (below) with the account directory and the case records together with their salts; a case record that names customers belongs to the customer data ("Access chain", item 5).

**What is public.** Day entries, day leaves, the protocol key list (§9.9), the role list and the list of countersigning keys (§9.11) are public and contain only hash values, dates, sizes and public keys with their validity data. Pages of the anchor history (§9.7) and extracts of the log contain `chain_id`, sizes, roots and times, the pages in addition the affiliation indication (§9.10); the server hands them out only when the request names the `chain_id`. No object that can be fetched without a `chain_id` carries customer data, a commitment, an `appliance_id` or a `chain_id` in cleartext; excepted are the access chain statement and its day heads ("Access chain", item 9), which carry only `chain_id`, `appliance_id` and countersignatures of the access chain, a chain without customer data (item 6 there).

**Information barrier.** An affiliated party in this section is every party other than the vendor itself that stands in one of the relations 2 to 8 of §9.10 with the vendor. A person in a key management position of the vendor is no affiliated party insofar as it acts for the vendor; for such a person the affiliated parties from relation 7 are its close family members, the parties controlled by one of these persons, and the person itself insofar as it acts as a customer or for another party. The vendor MUST separate the customer data from every affiliated party, even if that party is a customer:

1. Access to customer data, to administrative accesses, keys and access tokens of the metadata server, to backups, operational logs, the alarm mailbox and the order system is held only by persons and systems of the vendor, each as far as their task requires it. No person acting for an affiliated party and no system of such a party holds an account, a key or an access token for this. The vendor runs its services in deployment projects of its own; it shares accesses, servers, backup targets and mailboxes with no affiliated party.
2. The vendor passes nothing about other customers on to an affiliated party, not even summaries, counts or analyses (device numbers, use, sectors, provider mix), except what it publishes for everyone.
3. An affiliated customer receives what every customer receives: the same prices, terms and paths to licenses, no additional telemetry, no additional endpoint and no direct access. Every administrative action on a license (issue, renewal, takeover) is permitted only with a recorded justification, whether or not its customer is affiliated; so no administrative path branches on the affiliation. The justification is the purpose as a category (format specification 4.25, `purpose`) with the record to which the entry of the access chain is bound, for a change of the affiliation register the reason with case number (§9.10, obligation 1).
4. Recipients of vendor-side alarms (§10) are not persons acting for an affiliated party.
5. Every change to the affiliation register and every administrative action on a license, whether or not its customer is affiliated, is recorded immutably with person, time and justification, from the start of the access chain in it (below).
6. The affiliation register and the declarations (§9.10, obligation 2) are read only by the statements service (§9.11), which issues pages of the anchor history, and by the administration tool in a recorded query, which from the start of the access chain is recorded in it (below); the path that records a new declaration compares it only with the declarations of the same license. A declaration that the server has not accepted is output by the system holding it only to the person who enters it with the administration tool; that access is recorded like any other (access chain, items 1 to 3). Whether customers are affiliated or have declared an affiliation, and how many, appears in no other output, not even in `/v1/status` or in a report to a mailbox, and no response names the content of a declaration. Tools for backups and their checks name no number of rows or entries for the register and the declarations; they show their completeness with a seal, for instance an HMAC with one key per store.
7. The vendor does not record fetches of the anchor history (§9.7) and of the vendor log (§9.9): no `chain_id`, no `appliance_id` and no source address beyond the rate limiting in memory; operational logs name no `chain_id` of these fetches. Who audits which chain when, it passes on to nobody, not even to an affiliated party.
8. The vendor MUST have adherence to this section audited at least once a year by a party independent of it as long as an access chain exists (below, item 8 there) or it makes use of the exception below, and SHOULD do so regularly otherwise; it makes the result accessible to the customers.

**Access chain (from edition 1.10).** The vendor records accesses to customer data in a LEDGER chain that it runs for this purpose, with entries `DATA_ACCESS` (format specification 4.25). The access chain starts at the latest on the earlier of two days: `erster_tag` of its vendor log (§9.9) or the day on which a server of edition 1.10 first operates. The vendor states its start beforehand at both places of publication (item 9). Until its start items 5 and 6 above and exception (c) below apply in the form "recorded immutably" without an access chain.

1. **What is recorded.** Every access by a person to what item 1 of the information barrier names, one entry per data class; every change and every query of the affiliation register by a person; every administrative action on a license, whether or not its customer is affiliated; every opening of fillers (§9.9). Every command of the affiliation register, a query and the processing of declarations (§9.10, obligation 2) too, writes an entry of the same form: `data_class` = `affiliation_register`, `access_mode` = `change`, `scope` = `all_customers`, `purpose` = `affiliation_upkeep`. What it did stands in the record, and with person, time and reason in the register itself (item 5 of the information barrier); so the access chain shows neither whether and how many customers are affiliated nor when the register was changed (item 6 of the information barrier). An **access path** is every part that outputs or changes customer data for a person or at a person's request; it writes one entry per access under the `actor_id` of that person (item 2). Only a part whose output no person reads directly counts as a **service**, for instance the statements service, which issues pages of the anchor history and reads the affiliation register for that, or the closing of the vendor log; a service is recorded once per start and data class with its standing purpose (`actor_kind` = `service`, `purpose` = `service`), never per request. If a service performs administrative actions on licenses without a person of the vendor triggering them (for instance issue, renewal, takeover, end or key replacement after a purchase, a payment or a notice of the customer through the order system), it additionally records them in **collective entries**: for every UTC day `d` from the start of the access chain and every data class with which it is recorded per start, exactly one entry with `actor_kind` = `service`, `purpose` = `license_admin`, `access_mode` = `change`, `scope` = `all_customers` and `ts_captured` = `end(d)` (§9.9), all entries of a day with the same `access_id`, also on a day without any action, written after `end(d)` and at the latest 24 hours after it. Its case record names every action of the service on that day that changes customer data, with time, kind, license and occasion; it is the case record to which their justification is bound (item 3 of the information barrier), and the account of the service takes the place of the person (item 5 there). So number and form of the entries do not depend on the number of purchases, and every such action is bound in the access chain at the latest 24 hours after the end of its day. If a part outputs customer data to a person, it is an access path for that output, even if it otherwise works as a service. A service that writes customer data into a mailbox, a file or a log does not thereby output them to a person; whoever reads them there accesses by another route (item 3). Fetches per item 7 of the information barrier are not accesses in this sense.
2. **Before the access.** Every access path the vendor operates through which customer data are output or changed writes the entry with `capture` = `gate` and outputs data only once the access chain has confirmed it (format specification 8.7). If the access chain cannot be reached, the access path MAY output data to a person without confirmation; the person enters the access with `capture` = `emergency` within 24 hours, and the audit per item 8 of the information barrier names every such case. A service is not an access path: it records its entry per start durably for delivery before it first accesses customer data and delivers it with `capture` = `gate` through the import interface, but does not wait for the confirmation; if it cannot record the entry durably, it does not access. It delivers its collective entries (item 1) in the same way. So a service whose account already stands in the access chain per item 4 does not depend on whether the access chain can be reached.
3. **Entered by the person.** An access by another route (access to the machine, file of the database, backups, operational logs, mailbox) is entered by the person with `capture` = `declared` before the access, otherwise at the latest 24 hours after it.
4. **Accounts.** Every person accesses with an account of their own. The account directory assigns every `actor_id` to a person or a service, says whether the person also acts for an affiliated party, and is only appended to. Every addition, also one that only changes the indication of an affiliated party, stands in the access chain before it takes effect and before the account first accesses: as an entry `DATA_ACCESS` with `data_class` = `credentials`, `access_mode` = `change`, `purpose` = `maintenance` and `scope` = `all_customers`, whose case record is the addition itself (the `actor_id`, whom it denotes, whether the person also acts for an affiliated party, and from when). An account whose addition does not stand in the access chain beforehand does not access.
5. **Case records.** For every entry the vendor records the case record and its salt and only appends to this record. A case record that names customers is itself customer data.
6. **What no entry names:** a `chain_id`, an `appliance_id`, a customer identifier or a name.
7. **Operation.** The access chain SHOULD run on an installation that is separate from the metadata server and whose administration is held by no person acting for an affiliated party. It is anchored like every chain (§9.1, §9.9), MUST carry at least one time witness per day from an authority operated neither by the vendor nor by a party affiliated with it (format specification 7.3), and its affiliation indication is `vendor` (§9.10).
8. **Audit.** As long as an access chain exists, the audit per item 8 of the information barrier is mandatory, at least once a year. It receives verification packages of the access chain over the whole time since its start, the account directory and the case records with their salts, and it
   - recomputes the commitments of the case records, those of the additions to the account directory (item 4) included, and checks that every account accesses only after the entry of its addition;
   - compares every published day head (item 9) with the package: for its `tree_size` t, t ≤ N and `root(t)` = `merkle_root` hold (format specification 7.4.10);
   - checks for every day since the start, in the published day leaves (format specification 7.4.9), whether the position of the access chain (format specification 7.4.3) stands there; if it stands on a day for which the package carries no receipt, the chain has been truncated or rewritten;
   - names every entry with `capture` = `emergency`, every day without a time witness per item 7 and every day for which a collective entry per item 1 is missing or was chained later than 24 hours after `end(d)`, and compares the case records of the collective entries with the order system.
9. **Publication.** Before its start the vendor publishes at both places of the vendor log (§9.9) the **access chain statement** `{"format": "ledger-zugriffskette/1", "beginn": <date>, "ketten": [{"chain_id": <uuid>, "appliance_id": <uuid>, "ab": <date>}, …]}`; a chain succession of the access chain (§9.2 step 1) adds an element and never changes one. For every UTC day `d` from the start the vendor publishes by `end(d)` + `P` (§9.9) at both places the **day head** of the access chain: the countersignature (§9.1, all six members) of its chain with the greatest `tree_size` among those with `day(server_ts)` ≤ `d`, as long as there is none, `null`. Place 2 accepts only additions here too. Because the access chain carries no customer data (item 6), its `chain_id` and `appliance_id` are public: anyone can fetch its anchor history (§9.7) and its extracts and recognise its active days in the day leaves.

The access chain shows which accesses were recorded, when, through which account, for what purpose and in what scope, and that an anchored entry was neither removed nor changed afterwards. It does not show whether every access was recorded (no evidence produced by LEDGER).

**A person acting for both sides.** A person who acts at the same time for the vendor and for an affiliated party holds no operational access to customer data, administration tools, access tokens of the fleet or backups; signing key lists offline with the vendor root remains possible for that person. As long as the vendor cannot arrange this, such a person MAY, by way of exception from item 1, keep operational access if all of the following hold: (a) the vendor states the exception publicly with its scope and a fixed day on which it ends; after this day it no longer applies, and an extension is a new statement published in the same way. (b) Heartbeats with their counters, telemetry, the filler secret, openings of whole days (§9.9) and every summary about other customers remain closed to that person; item 2 applies to that person without exception. To this end every access path refuses to an account that the account directory lists as also acting for an affiliated party (access chain, item 4) every access with `data_class` `heartbeat`, `affiliation_register`, `backup` or `store` and every read and export with `scope` `several_customers` or `all_customers` (format specification 4.25), and moreover every access as long as the statement per (a) is not published and after its end day; such an account holds no access to a machine, a database or a backup that contains heartbeats, and none to the filler secret. This depends on the account alone, never on the affiliation of the customer whose data are concerned. (c) Every access of that person to customer data, administration tools, access tokens or backups is recorded immutably with time, object and reason, from the start of the access chain in it. (d) The audit per item 8 is mandatory for the duration of the exception and covers these records.

**Equal treatment.** Anchor history (§9.7) and vendor log (§9.9) treat every chain alike: the same formats, routes, limits, deadlines, response times and error responses, whether or not its customer is affiliated with the vendor, whichever edition or license it has, and whether or not the installation belongs to the vendor itself. The part of the server that forms the log reads for this only the leaves and the binding of every chain to its appliance, never license, customer or affiliation register; the member `affiliation` is formed only by the statements service, which issues pages of the anchor history (§9.11, item 6). Countersigning, gap witnesses and quotas (§8, §9.1, §9.2, §9.5) follow the same rules for an affiliated customer as for any other. The criteria of this specification name formats, not a particular vendor: every vendor with its own root, its own keys, its own `log_id`, its own filler secret and its own time-stamping authorities reaches the same results.

**What no verification package shows.** For adherence to this section: no evidence produced by LEDGER. No verification package and no verifier shows whether the vendor separates the customer data and does not record fetches (format specification 11.2); the audit per item 8 stands for that. Whoever fetches the anchor history or the log tells the vendor which chain is audited when; that the vendor does not record this is a duty of its operation per item 7. The access chain shows the recorded accesses, not that every access is recorded.
